# v2 M2 — implementation plan (agents)

Goal (from [`2026-08-06-ade-v2-core-design.md`](../specs/2026-08-06-ade-v2-core-design.md) §7 M2,
as reshaped by sketch **§7c**, which is binding and post-dates §5.1):
`agents-core` + `claude-code` live, `StopPolicy` ported tests-first, the plugin
transport swapped, badge/notifications, the reconciliation sweep.

**The exit, concretely:** a real `claude` running in a v2 pane drives a real state
indicator. Its hooks reach the app over `hooks.sock`, the ported `StopPolicy`
reduces them, attention aggregates, and the dock badge and a notification follow.

Predecessor: [`2026-08-07-v2-m1-plan.md`](2026-08-07-v2-m1-plan.md) (green at
`fd5910a`, 699 tests, all six smokes). Branch: `v2-m2-agents`, off `master`.

Status: **reviewed and ready to execute** — one feasibility review, two advisor
passes, six baseline smokes verified green. The
review found one blocker that reaches the user's live v1 app (now D2), one
correctness bug in the wire format (D12), and one phase that could not be built as
scoped (the headless seam, now out of scope). All three are folded in below.

## Probes already run (both green, 2026-08-07)

Design questions settled empirically before writing, the habit that retired
`better-sqlite3` in M1. The second one invalidated a decision this plan had
already written down.

1. **`node-pty`'s `IPty.process` reports the pty's FOREGROUND process on macOS.**
   Measured: an idle `zsh` reads `"zsh"`, `sleep 4` running in it reads
   `"sleep"`, and it returns to `"zsh"` when the sleep ends. So review §Bad-5's
   reconciliation sweep — *state says working but nothing is running* — needs **no
   subprocess and no `ProcessAPI`** (which is M3). Without this probe the sweep's
   only input would have been a `ps` shell-out, dragging `ProcessAPI` a milestone
   forward to serve one boolean.

2. **A vendor's foreground process name is NOT its command name.** `claude` on
   this machine is `~/.local/bin/claude` → a binary literally named `2.1.224`, and
   macOS derives `p_comm` from the **resolved** executable. Measured: the pty
   reports `"2.1.224"`, never `"claude"`. The first draft of D6 had each agent kind
   identify itself by matching the foreground process name against its own — a
   predicate that would have **matched nothing on this machine**, so the sweep
   would have demoted every live agent while every unit test passed. D6 is
   rewritten below and no longer matches names at all.

Both go in an ADR at the end of M2.

## Decisions taken here, not left to the executor

Twelve, each because the alternative is a half-built seam nobody can test in.
**D1, D3, D10, D11 and D12 are deviations from a written spec** and are flagged as
such; the rest resolve gaps the specs left open.

### D1 — the kernel injects the correlation env, not `claude-code`

**Deviates from core-design §5.2 and the handoff's step 5**, both of which give
env injection to `claude-code` via `sessions.onWillCreate`.

It cannot be built that way. `SessionHost.onWillCreate` is **synchronous by
documented design** (`session/host.ts:98-119`: "`create` returns a `SessionID` that
the layout needs in the same tick; an async hook would make session creation a
promise and every caller a state machine"), and an extension runs in a utility
process reached only by request/response over a port. The file already names the
escape hatch: *"a hook that needs IO does it at registration time and closes over
the answer."*

Both values are kernel facts anyway. `SHEPHERD_SESSION_ID` is core's own declared
correlation key ("THE correlation key, everywhere"), and the events socket is
core's own front door. **v1 agrees**: the *app* injected the env per pane and the
plugin only ever read it. So `main/index.ts` registers one in-process
`onWillCreate` hook and every session gets the correlation env, whether or not any
agent extension is loaded.

*Considered and rejected:* a declarative env contribution — a new `ApiCall`
carrying `Record<string,string>` with `${sessionId}` placeholders, expanded
main-side. Buildable, and it preserves §5.2's letter, but the machinery would
exist so that an extension could declare two constants the kernel already owns.
Recorded in the ADR as considered, not built.

What `claude-code` still owns, which is the substance of §5.2: the plugin
(`hooks.json` + `report.sh`), the `claude.hook` subscriber, `StopPolicy`, and
resume. It loses only the part that was never vendor-specific.

`sessions.onWillCreate` stays typed in the SDK and keeps refusing across the port
— with its reason corrected from `LANDS_IN('M2 (agents-core)')` (`api.ts:359`) to
the synchronous-callback one, because "it arrives in M2" becomes false the moment
this lands, and a stale refusal is worse than an honest one.

### D2 — v2 must STRIP v1's env vars, and this is the highest-value line in M2

**The one finding here that can damage something the user relies on.** It is the
first item of P1, ahead of the injection it protects.

v2 does **not** inject only into its own ptys — it inherits `process.env`
wholesale. `shell.ts:35-42`'s `STRIPPED` set names eight variables, none of them
`SHEPHERD_*`, and `shell.ts:48-53` copies every other key through;
`ipc.ts:218` uses `{ ...defaults.env }` because the renderer deliberately sends no
env of its own (`session-spec.ts:8-10`).

So, measured in the session this plan was written in: a shell in a **v1** pane
carries `SHEPHERD_TAB_ID=7D0CD503-…`, `SHEPHERD_SOCK`, `SHEPHERD_CTL_SOCK` and
`SHEPHERD_PTY_SOCK`. Running `pnpm dev` from such a pane — this machine's
documented daily workflow — hands all four to v2's Electron main, which hands them
to **every v2 pane**. v1's globally-installed plugin fires on exactly
`[ -n "$SHEPHERD_TAB_ID" ] && [ -n "$SHEPHERD_SOCK" ] && [ -S "$SHEPHERD_SOCK" ]`
(`claude-plugin/hooks/report.sh:24`) — a predicate confirmed satisfied right now.

M2 is the milestone that puts a real `claude` in a v2 pane. Without this fix, the
first dogfood run posts `{tab_id: <a v1 pane>, event: Stop|PermissionRequest|…}`
to the **live v1 app**, and the v1 pane that launched the build starts flipping
working/blocked/needsCheck, badging the dock and firing notifications on behalf of
an unrelated v2 agent. `SHEPHERD_CTL_SOCK` is the same leak one door along: v1's
`shepherd` CLI, run in a v2 pane, drives the live v1 app.

**The fix cannot live in D1's hook.** `WillCreatePatch` is merge-only
(`host.ts:346` is `{ ...current.env, ...patch.env }`, with no delete channel).
It belongs in `shell.ts`'s `STRIPPED`, which is the one place that already decides
what a session does **not** inherit, and it is pinned by a test asserting a created
session's env contains none of the four.

This also corrects D10's reasoning. The plan's earlier instinct — "that safety
rests on a guard in a file we are replacing" — was right to be nervous and wrong
about where: the safety rested on an env inheritance nobody had written down, in a
file nobody was replacing.

### D3 — `viewing` reaches the child as one pushed boolean per session

The handoff offers two options — build a pushed mirror, or thread `viewing` into
the event payload the child already receives. **Take the mirror, at its minimum
size**, because the second cannot serve the case that actually bites.

Threading per event covers `StopPolicy`'s landing (a `Stop` under your eyes lands
`idle`, ADR 0020). It does **not** cover the other half of v1's table: *looking at
a pane clears need-to-check*. That is an edge with no hook event behind it, so
there is nothing to thread it onto — and a poll for it would be v1's bug exactly
(`didFocus` only fired on a focus *change*). Core's `AttentionStore` clears the
*attention channel* on that edge (`store.ts:269-273`) but nothing clears the
*agent state*, which is a different thing living one process away.

So: `ViewingResolver` — still the one and only predicate — has every edge
published as a bus topic, `session.viewing` `{sessionId, paneId, viewing}`, for
panes bound to a session. `agents-core` keeps a `Set<SessionID>` fed by it and:

- passes `viewing: viewed.has(id)` into the kind's state machine, and
- on a `false → true` edge, re-lands `needsCheck → idle` for that session.

This is a **cache of the one answer, not a second check** — nothing in the child
recomputes front-ness from focus, zoom or overlay, which is what ADR 0020 forbids.

**The publisher goes in main, not in `ViewingResolver`.** The resolver takes no
`EventBus` today (`viewing.ts:36`); main already consumes it the same way
`AttentionStore` does, so subscribing `onDidChangeViewing`, resolving the session
via `layout.sessionFor(pane)` (`layout/store.ts:243`) and emitting is the smaller
change and keeps core's resolver dependency-free.

**The ordering property, which must be written down and tested:** `claude.hook`
(from `EventsIngress`, `events-ingress.ts:81`) and `session.viewing` land on the
**same** `EventBus`; `EventBus.emit` fans out **synchronously** (`bus.ts:90-99`);
`ExtensionHost` posts each straight to the one port (`ext-host.ts:664-675`). One
bus, one port, FIFO — so a hook event and a viewing edge **cannot reorder**. This
is what makes the mirror safe, and an untested invariant is a coincidence.

Known transient, and it is an argument *for* the re-land rather than against the
design: core clears attention synchronously while the child's agent state is still
`needsCheck` until the port delivers. The `false → true` re-land heals it.

### D4 — `points` move to the SDK and run in the child

`registerAgentKind` carries `detect`, `stateMachine`, and (§7c) `headless.argv` /
`headless.parse` — all **functions**, which cannot cross a port. They do not have
to: §7b puts every extension service in **one** utility process, so `agents-core`
and `claude-code` share an address space and an in-process point registry is the
correct implementation rather than a compromise.

`boundaries.js:242-257` denies `@shepherd/core` in `app/src/ext-host/**` as a
group (so subpaths go with it), and that denial is right — a core import there
would be a second, empty kernel. Core's `PointRegistry` is pure, zero-dependency,
imports only `@shepherd/sdk`, and has **no consumers in core**. So it relocates to
`packages/sdk`, which is where core-design §4.7 puts it anyway ("the SDK ships a
standard extension-point primitive"). Core re-exports it so nothing outside moves.

Two rules keep §7c honest, both enforceable in the child:
- `define` records its owner; a second `define` of the same id is a typed refusal,
  not a silent second registry.
- `get(id)` resolves only if the caller **declared the point's owner** in its
  manifest `dependencies`. The `activate` ask already carries the manifest
  (`ext-protocol.ts:211`) — note `runtime.ts`'s `#activate` currently ignores it
  entirely, so this is new plumbing on an existing field. Declared, not discovered.

### D5 — an extension may export an API, and `extensions.get` becomes real

`claude-code` must reach `agents-core`. Today `activate` returns `void` and
`ExtensionsAPI` refuses with `ACROSS_A_PORT` — which stops being true under D4:
both extensions are in *this* process.

`ActivateFn` gains a return value (`void | T | Promise<void | T>`); the child
runtime records it per extension; `extensions.get<T>(id)` resolves it, gated on
the same declared-`dependencies` check as D4, and `isActive(id)` answers from the
same table. Activation **ordering is already correct** — `ExtensionRegistry.#run`
(`registry.ts:268-275`) awaits `manifest.dependencies` before the activator, and
its cycle check is the documented landmine, so nothing is added there.

Two things this must get right:
- **The cross-process case must be a typed refusal naming the other process, never
  `undefined`.** `api-kernel.ts:200` types `get<T>(id): T | undefined`, and
  `undefined` already means "not active" — so a silent miss would make "in another
  process" and "not running" indistinguishable, which is the exact ambiguity
  `api.ts`'s doctrine exists to remove. Nothing runs in a second process today;
  the refusal is written now so the day it does is a message, not a mystery.
- **One owner for the dependency gate.** `ExtensionRegistry.apiFor`
  (`registry.ts:164`) already implements this judgement, with its own tests, and
  has **zero production callers**. Resolution happens in the child, which cannot
  import core — so P2 **deletes `apiFor` and its tests**. Two implementations of
  one judgement is precisely the drift `boundaries.js` exists to prevent, and the
  unused one is the one to lose.

### D6 — the sweep asks "is the shell back in front", and never matches a name

*Rewritten after probe 2.* The first draft had each kind identify itself with
`detect(foregroundProcess)` — matching the vendor's own command name. Probe 2
shows the foreground name is `2.1.224`, so that predicate matches nothing, and the
sweep would have demoted every live agent.

The sweep does not need vendor detection at all, because it asks a simpler
question that is vendor-blind by construction:

```
hasForegroundProcess(session) := basename(pty.process) !== basename(session.command)
```

A pane's session command is the login shell. While `claude` runs, the foreground
is *something else* — whatever it happens to be called. When `claude` dies by any
means, the foreground returns to the shell, which **is** the session's own command.
No name table, no vendor knowledge, and immune to a version-named binary.

The advisor's objection to this shape — that it inverts for a session whose
command **is** the agent (a headless `claude` would read idle while alive) —
stands, and is answered by not using the sweep there: such a session's liveness is
its exit, which is exact.

**Which session is an agent is answered by the hooks, not by a process name.**
`SessionStart` says so and carries Claude's own session id. That is the correlation
ADR 0003 established, and reaching for a process name was a second, worse source
of the same fact.

`SessionHost` therefore gains `foregroundProcess(id): string | undefined` over the
probed `IPty.process`, and a `sessions.list` command (permission `sessions`)
answers `{id, cwd, command, foregroundProcess, hasForegroundProcess, cols, rows,
paneId}` per live session. **`Session.hasForegroundProcess()` is already declared
in the SDK** (`api-sessions.ts:69`, "the liveness reconciler's input") — it is
implemented by this field rather than left typed-and-unmentioned, because a
declared member with no story is the drift `api.ts` refuses.

### D7 — agent state and attention are two channels, and only one of them alerts

`AttentionLevel` is `none | info | attention | urgent`. It has no `working` and no
`idle`, so **attention cannot drive the indicator** — Flock rule 8's five states
(standing / walking / grazing / butting the fence / tipped over) are *agent*
states. Conflating them would put `working` on the dock badge.

- `agents-core` owns `AgentState` (`shell | idle | working | blocked | needsCheck
  | error`, ported from v1) and publishes `agents.stateChanged`
  `{sessionId, state, reason?, turnFinished}` on the bus.
- It maps that onto attention, and this mapping is the **only** place agent state
  becomes an alert: `needsCheck → attention`, `blocked | error → urgent`,
  everything else → clear. Core's `AttentionStore` already clears `attention` (and
  deliberately not `urgent`) on the viewed edge, discriminating on **level, never
  reason text** — so v1's table survives with no second implementation.
- `turnFinished` rides the state event, never `state === needsCheck` — the viewing
  landing makes the latter miss (ADR 0020, and CLAUDE.md says so twice).

`decide()` has **zero production callers** today (only `store.test.ts`); M2 is
where it gets plugged in, in main: banner/chime from the agent-state event (the
only thing that knows `turnFinished`), badge count from `attention.count()` via
`onDidChange`.

### D8 — only `agents-core` declares the `attention` permission

The handoff's "`agents-core` is the ONLY writer of attention for agent sessions"
is currently held by discipline. Narrow it: `claude-code`'s manifest declares
`sessions` and `storage` and **not** `attention`, and its transitions reach
attention only by returning them from its registered kind.

**Stated precisely, because the first draft overclaimed it.** This is enforced by
manifest review (`PermissionStore.review`), not by construction: a third-party kind
that declares `attention` and is granted it can still write directly. And because
`api.ts:283-299` routes `attention.set/clear` through `services.tell`, a denial
reaches the extension as a **log line**, not a value — an extension that wants to
see the verdict must invoke the command itself, as `diagnostics.probeDenied` does.
What the decision buys is that our own built-in cannot drift into a second writer
without a manifest change showing up in review.

### D9 — two id spaces, named apart

Shepherd's `SessionID` (the pty, the value of `SHEPHERD_SESSION_ID`, the
envelope's `session_id`) and **Claude's** `session_id` inside a hook payload are
different things, and v1 conflated names around them.

- `sessionEventAccepted(sid, owner)` ports verbatim from `StopPolicy.swift:30`.
  The bug it kills is live in v2: a nested `claude -p` run via Bash inherits the
  parent's env and fires hooks tagged with the parent's `SessionID` but carrying
  its own Claude `session_id`.
- Per review §Ugly-4, the one field splits in two: **`ownerClaudeSessionID`** (the
  ownership lock, taken on `SessionStart`, released on `SessionEnd`) and
  **`resumeSessionID`** (the `--resume` target). v1 held them apart with a
  side-effecting clear in an unrelated function.

### D10 — the env vars are `SHEPHERD_EVENTS_SOCK` and `SHEPHERD_CONTROL_SOCK`

**Deviates from `events-ingress.ts`'s doc comment**, which writes `SHEPHERD_SOCK`
(as does v1). v2 has **two** sockets and `SHEPHERD_SOCK` names neither; more to the
point, v1 owns that name on this machine and means something incompatible by it
(`nc -U` framing rather than HTTP).

Coexistence is then explicit and checkable: **different env var, different plugin
directory** (`~/.claude/skills/shepherd-v2`), so a `claude` in a v1 pane fires
v1's hooks and no-ops v2's, and the reverse. v1's own plugin needs no edit and gets
none — no `spike/` or `claude-plugin/` file appears in an M2 diff, and installing
at a different path makes ADR 0005's v1-symlink case unreachable rather than
merely handled. The ingress doc comment is corrected in the same commit that
introduces the variable.

**This decision is necessary but not sufficient on its own — D2 is what actually
closes the hole.** A different variable name does nothing while v1's variable is
still present in the environment.

### D11 — `report.sh` uses no `jq`, and needs none

**Deviates from the handoff and from `events-ingress.ts`'s doc comment**, which
both prescribe "one `jq -cn` builds the whole envelope".

That prescription is right about the *problem* and one design step behind the
solution. `jq` was proposed to fix v1's hand-rolled escaper — and the escaper only
existed because v1 **extracted fields in bash** (`tool_name`, `error_type`,
`session_id`) and spliced them into a string. This plan already moves extraction
to TypeScript (`payload.hook` rides whole), so **there is nothing left to escape**:
the only interpolated values are `$event`, a fixed name we write in `hooks.json`,
and the session id, a UUID the kernel mints. Neither can contain a quote.

Embedding an already-valid JSON document inside JSON is **concatenation, not
parsing**. So the envelope is three `printf`s around a verbatim splice — three
rather than one because a large `AskUserQuestion` payload in a single `argv` is an
`ARG_MAX` risk — with a one-character validity guard (`case $payload in '{'*)`)
falling back to `hook: null`.

Three things this buys, measured rather than argued:

- **`jq` is not on stock macOS.** On this machine `curl` is `/usr/bin/curl` and
  `jq` is `/opt/homebrew/bin/jq`. Requiring it silently breaks the plugin for any
  user without Homebrew — which is why v1 carried a `grep`/`sed` fallback that
  then lost newlines.
- **It restores ADR 0004's actual invariant** — zero JSON parsing and **zero
  subprocesses** on the common path. The architecture review records that the
  invariant had already crept back in v1 once `jq` became survivable; removing the
  tool stops it recurring by construction rather than by memory.
- Verified against payloads containing newlines, escaped quotes, backslashes and
  multi-byte unicode — the exact class v1's escaper turned into invalid JSON and
  therefore dropped in silence.

The one property to state, because it is the only real objection: a hostile
payload cannot spoof the envelope. `session_id` is written **before** the splice,
so a document that escapes its position can at worst add keys *inside* `payload`,
and anything that does not still parse is answered by the ingress with a logged
400. The top-level correlation key is unreachable from inside the payload.

### D12 — the hook sends NO `seq`; the bus numbers it

**Deviates from core-design §4.4/§5.2 and the handoff's step 5**, which specify a
per-session `seq` on the hook envelope. As designed it was not a diagnostic — it
was a **silent event-drop**, on exactly the events this milestone is measured on.

A per-session counter file is read-increment-write with no lock (stock macOS has
no `flock`). Two hooks racing — and subagent events genuinely are concurrent —
both read N and both POST `seq: N+1`. The second is then **dropped before
delivery**: `seqVerdict` returns `duplicate` for `seq <= lastSeen`
(`envelope.ts:31`) and `EventBus.emit` does `return` ahead of the fan-out
(`bus.ts:76-79`). A dropped `Stop` strands the pane at `working` forever; a
dropped `PreToolUse[AskUserQuestion]` never goes `blocked`. The first draft's
justification — "a lost increment is visible rather than harmful" — was backwards:
a lost increment produces a *duplicate*, not a gap, and the duplicate is the one
verdict that is not delivered.

So the envelope omits `seq` entirely and the bus numbers per source
(`bus.ts:71-74`), keyed `agent:<sessionId>` — already exactly per-session. Nothing
can be dropped, and ordering is arrival order.

What this gives up, said plainly: hook-side ordering detection. A hook lost in
transit (a `curl --max-time` expiry) is now invisible rather than showing as a gap.
That is the correct trade — a diagnostic is worth less than the events it was
dropping — and if it is ever needed the cheap fix is to make `duplicate` a
deliver-and-warn for `agent` sources rather than to reintroduce the counter.

## Constraints (bind the executor)

- Everything under `v2/`. The Swift app in `spike/` and the v1 plugin in
  `claude-plugin/` are **reference material and are never edited** — neither
  appears in any M2 diff.
- **`env -u NODE_OPTIONS` on every hand-run command.** An ambient `NODE_OPTIONS`
  makes Electron exit 9 before running a line of our code, and the symptom is
  every check failing at once with nothing explaining why.
- **`tooling/eslint/boundaries.js` IS the architecture diagram.** `extensions/**`
  may import `@shepherd/sdk` and nothing else — which is the point, since a
  built-in reaching into the kernel would stop being proof the public API
  suffices. If a phase seems to need a new exception, **stop and report** rather
  than widening it quietly. D4 is deliberately arranged to need none.
- **`erasableSyntaxOnly` is on**: no enums, no namespaces, **no constructor
  parameter properties**. Electron type-strips the main entry, so those are a
  *launch* failure a passing test suite will not catch.
- **Nothing calls `Date.now()` or a bare `setTimeout`.** `Clock` is injected. The
  reconciliation sweep is a timer machine (review §Bad-9's class) and gets
  fake-timer tests — that is the whole reason it is cheap to write here.
- **Every failure is a value at every boundary a caller can reach across.** Typed
  error, logged, never a silent no-op.
- **Pure first, tests-first.** Each phase's decision logic is a pure function with
  its own test file; the IO shell around it stays thin enough to read.
- A phase is done when it is **committed green** — `pnpm typecheck`, `pnpm lint`,
  `pnpm -r test` with the **count moved** (baseline **699**, `pnpm test:count`),
  and **all six smokes** passing (`smoke`, `smoke:session`, `smoke:terminal`,
  `smoke:isolation`, `smoke:single-instance`, `smoke:m1` — plus `smoke:m2` once
  P5 lands) — with a 3-line summary and an explicit `deviation:` field.
- **Verify a subagent's claims, never its report.** Run the gates yourself, and
  `ListAgents` before declaring anything complete.

## Phases

### P0 — the pure ports (no wiring)

The highest-value artifact in the rewrite, and it translates mechanically
(`StopPolicy.swift` is 87 lines with no AppKit and `viewing` already a parameter;
`StopPolicyTests.swift` carries 25 test functions including negative controls).

- Package skeletons for `extensions/agents-core` and `extensions/claude-code`
  (package.json, tsconfig, vitest config). Called out because P0 is otherwise
  described as "no wiring" and the count gate cannot run without them.
- `agents-core/src/state.ts` — `AgentState`, `StateTransition` (`state`,
  `reason?`, `clearTitle`, `applied`, `heldForBackground`, `turnFinished`).
  Vendor-blind: no Claude event name appears here.
- `claude-code/src/stop-policy.ts` — `applyEvent` and `sessionEventAccepted`, with
  `viewing` **as a parameter**. The ordering guard, the background-`Stop`
  suppression and the viewing landing are all deliberate; do not "fix" them.
- Tests translated from the Swift, negative controls included.

### P1 — the kernel affordances M2 needs

**First item: D2's strip.** `SHEPHERD_TAB_ID`, `SHEPHERD_SOCK`,
`SHEPHERD_CTL_SOCK`, `SHEPHERD_PTY_SOCK` join `STRIPPED` in `shell.ts`, pinned by
a test asserting a created session's env carries none of them. It goes first
because everything after it puts an agent in a pane.

Then:
- **D1's injection** — one `onWillCreate` in main; every session gets
  `SHEPHERD_SESSION_ID`, `SHEPHERD_EVENTS_SOCK` and `SHEPHERD_CONTROL_SOCK`. The
  ingress doc comment is corrected in this commit (D10).
- **D6's `SessionHost.foregroundProcess`** + the `sessions.list` command carrying
  `hasForegroundProcess`.
- **D3's `session.viewing` topic**, emitted from main. One emitter, no new
  predicate, plus the FIFO-ordering test D3 names.

### P2 — the extension-host affordances

- **D4**: `PointRegistry` relocates to `packages/sdk` (core re-exports); the
  child's `createPoints()` becomes real, owner-recorded and dependency-gated off
  `ask.manifest.dependencies`.
- **D5**: `ActivateFn` may return an API; the runtime records exports;
  `extensions.get`/`isActive` resolve in-process, dependency-gated, with the
  cross-process refusal written now. `ExtensionRegistry.apiFor` and its tests are
  deleted.
- A child-side `sessions` subset — `list()` over `command.invoke`, plus an
  `onDidExit` bus topic so a session's death reaches the child (nothing routes
  `SessionHost.onExit` there today, and D6 leans on it for direct-command
  sessions). **Members that still cannot cross a port keep refusing, with reasons
  updated**; `api.ts`'s rule that a refusal is never `undefined` is not relaxed.

Exit: `diagnostics` still passes unchanged, and a test proves a point defined by
one extension is reachable by a declared dependent and refused to a non-dependent.

### P3 — `agents-core`

- The `agents.kinds` extension point it **defines** — §7c's first real consumer of
  `points.define`, and what makes `codex`/`opencode` third-party extensions rather
  than a fork. **`AgentsAPI.registerKind` is a thin wrapper over that point, not a
  second surface**: the point is the registry and the API is the convenience, so
  `agents-core` consults exactly one list. Building both independently would give
  a kind registered by API no path into the point's own ordering — the §7c reading
  is that the built-in routes its pluggable decision through its own seam, which
  only holds if there is one seam.

  **The contract, pinned here because P4 would otherwise force it to be rewritten.**
  The shape is decided by one constraint: `agents-core` must stay vendor-blind
  while `claude-code` needs the Claude `session_id` *out of the payload* before
  its reducer runs (the ownership lock, D9). So `agents-core` cannot pre-filter,
  pre-parse, or pre-validate anything — it hands the raw event over and takes a
  decision back:

  ```ts
  interface AgentKind {
    readonly id: string;
    /** Ingress topics this kind understands, e.g. ['claude.hook']. */
    readonly topics: readonly string[];
    /** Declared per §7c; asking for one a kind lacks is a typed error, not a hang. */
    readonly capabilities?: AgentCapabilities;
    reduce(input: AgentEventInput): AgentDecision;
  }

  interface AgentEventInput {
    readonly topic: string;
    readonly payload: unknown;      // the envelope's payload, untouched
    readonly current: AgentState;
    readonly reason?: string;
    readonly viewing: boolean;      // the mirrored ONE predicate, threaded in
    readonly slot: AgentSlot;       // this kind's own per-session state
  }

  type AgentDecision =
    | { readonly kind: 'transition'; readonly to: StateTransition }
    | { readonly kind: 'ignore'; readonly why: string };
  ```

  Three properties that follow, each of which is a bug avoided:
  - **`slot` is lifecycle-scoped**: created when a kind first adopts a session,
    dropped on session exit. Without it `claude-code` keeps a module-level map of
    ownership locks and resume ids that leaks every dead session — v1's
    `locatePane` sprawl reborn one layer in.
  - **`ignore` carries a reason and is a first-class answer**, because it is what
    both the ordering guard and a foreign nested `claude -p` produce, and those
    must be distinguishable in a log from "nothing happened".
  - **The sweep does NOT go through `reduce`.** `applyEvent` is Claude's protocol
    reducer; the sweep is vendor-blind evidence about a process. Synthesising a
    fake event to carry it would be eaten by the ordering guard, and would put a
    lie in the reducer's input. Both the kind's output and the sweep's demotion
    call **one internal `transition()`** on the agent record — one writer, two
    sources of evidence.
  - **The sweep demotes to `needsCheck`, never `idle`**, with a reason naming what
    happened ("claude exited without a SessionEnd"). A dead agent is precisely
    something the user has not seen; landing it `idle` would silently discard the
    one alert the sweep exists to raise.

- **Seeding the viewing mirror is not a mechanism of its own.** `sessions.list`
  carries a `viewing: boolean | null` per row (`null` = no pane, or not known),
  so the activation-time read that seeds the registry seeds the mirror too, and
  crash recovery is that same path re-run. Nothing in main knows when a child
  subscribes to a topic, and teaching the extension host to re-announce one
  particular topic would couple the kernel to an extension's vocabulary.
  **Order matters**: `event.on` is fire-and-forget while `sessions.list` is a
  round-trip, so an edge can land after subscribing but before the snapshot
  arrives. Subscribe first, **buffer** edges, fetch the snapshot, apply the
  snapshot, then apply the buffer — the ring's replay-then-live rule, one layer
  along, and for the same reason: no gap and no stale overwrite.
- The agent registry keyed by `SessionID`; the `session.viewing` subscription
  (D3); the state → attention mapping (D7); `agents.stateChanged` on the bus.
- The **reconciliation sweep** (D6), on an injected clock, running only while some
  session is `working`/`blocked`, demoting with a logged reason.

  **Four constraints on it, all measured during P1 rather than reasoned about.**
  Each would produce a sweep that looks correct and demotes live agents:
  - **`hasForegroundProcess` is tri-state.** `undefined` means the tty could not
    be read, and node-pty returns exactly that — it does not throw — on every
    darwin failure path. It is **not** `false`. The sweep must fail toward *not*
    demoting: a wrongly-demoted live agent is worse than a state that is briefly
    stale, and only one of the two self-corrects.
  - **Demote on consecutive readings, never one.** A single `false` can be a
    sampling artefact; a single `true` is not proof of life either.
  - **A pane must be spawned as the shell's own resolved path.** macOS derives
    the process name from the RESOLVED executable, so a session spawned as
    `/bin/sh` reports its foreground as `bash` and reads busy **forever** — the
    sweep would never demote it. This is the same root cause as probe 2 (claude's
    binary named `2.1.224`), biting the command side instead of the foreground
    side. `shellDefaults` uses `$SHELL` or `/bin/zsh` and is fine; a wrapper or an
    alias would not be. Pinned by a test.
  - **Ignore the first tick after spawn.** A freshly spawned pty reports
    node-pty's own `spawn-helper`, and a login shell runs transient helpers for
    the first ~150ms.
- **Crash recovery, which is the same mechanism.** `#forget` disposes host-side
  bus subscriptions, so hook events during host downtime are ACKed 202 by the
  ingress and delivered to nobody; after the one restart `agents-core` reactivates
  with an empty registry **and an empty `viewed` set**, which it cannot query
  across the port. So: the sweep is the crash-recovery path, and `viewed` is
  re-seeded on activation (main re-announces current viewing on subscribe).
- **Teardown**: the sweep timer, the subscription, the points it defines and any
  attention it set all land in `ctx.subscriptions` — but note the runtime disposes
  those **in the child**, so a crash runs none of them, and attention entries
  otherwise outlive the extension (only `#purge` on pane close clears them).

**Main keeps the last agent state per session, and that one map answers three
otherwise-separate failures.** They look unrelated and have a single fix:

| failure | without the map |
|---|---|
| host exhausted (restart spent) | the indicator freezes at its last value with attention still set |
| host **crash** | `ctx.subscriptions` never runs — it lives in the dead child |
| renderer reload mid-session | blank indicators until the next state change; with dev HMR this is constant, not rare |

So main maintains a `Map<SessionID, AgentState>` fed by the same forwarded
`agents.stateChanged` it already relays, and:

- **on renderer (re)connect**, snapshots the map down the new EMIT channel. This
  is D3's `viewed` re-seed one layer along — the same "a pushed channel needs a
  replay or its first frame is a blank" shape, which is worth noticing twice.
- **on host `stopped`/`exhausted`**, clears the map, clears attention, and pushes
  the cleared state so every indicator lands on a neutral *unknown* rather than a
  confident stale one — with the log line saying which of the two happened. A
  frozen `WORKING` after the host is gone is the "looks wired, does nothing"
  failure this project keeps paying for.

Clearing attention wholesale is acceptable **only while `agents-core` is the sole
writer** (D8), because `AttentionStore` does not record the caller that set an
entry and selective clearing would need bookkeeping nothing else wants. That
dependency is written here so the day a second writer exists, this is the line
that has to change.
- Its exported `AgentsAPI` (`registerKind`, `stateOf`, `onTurnFinished`).
- Manifest: `sessions`, `storage`, **`attention`** — the only manifest in the repo
  declaring the last (D8). Plus the mechanical wiring a new built-in needs: a
  `BUILTIN_MODULES` entry, a `workspace:*` dep in `packages/app/package.json`,
  tsconfig references, a vitest project. A manifest with no module compiled in
  answers `unavailable`, which `smoke:m1` will surface.

### P4 — `claude-code`

- Manifest: `dependencies: ['shepherd.agents-core']`, permissions `sessions` +
  `storage`, **no `attention`** (D8). Activation ordering comes free.
- Registers the `claude-code` kind: the state machine wrapping P0's `applyEvent`,
  and the ownership lock (D9). No name matching (D6).
- Subscribes `claude.hook`; splits `ownerClaudeSessionID` / `resumeSessionID`;
  parses `background_tasks` for ADR 0015's suppression **in TypeScript**, off the
  hook's critical path.
- **The plugin**: `hooks.json` + a pure-bash `report.sh`, no `jq` (D11), no `seq`
  (D12). It stays bash: ADR 0004 measured ~50ms of `python3` startup putting
  `PreToolUse` behind `Stop` and flipping the state, and node's ~40ms would do it
  again. Two further details settled so nobody re-derives them:
  - `curl --max-time 2`. Hooks are synchronous, so **the observer must not be able
    to stall the observed** (review §Ugly-4).
  - unparseable or empty stdin ⇒ `hook: null`, envelope still sent. Never lose the
    event: state is decided by the event NAME, so a lost payload costs a cosmetic
    reason string and nothing else.
- Plugin install as a command, porting `ClaudePluginInstaller`'s five-case
  classification: **create or repair, never replace** (ADR 0005), at
  `~/.claude/skills/shepherd-v2`.

### P5 — the visual, the alert channel, and the M2 smoke

The phase the milestone exit is measured on, and larger than one bullet suggests.

- **A new `EMIT` channel** (`channels.ts` has three today), preload exposure, and
  the `bridge.ts` surface type — whose `BRIDGE_SURFACE` test-lock must be updated
  deliberately.
- **Forwarding is a main-side allow-list**, whose first entry is
  `agents.stateChanged`. Not a renderer-chosen `subscribe(topic)`: `bridge.ts`
  already refuses a generic `invoke(channel, …)`, and this is the same widening in
  the other direction — under P4 a `claude.hook` payload carries the whole hook
  stdin, including tool inputs and prompts, which a compromised page must not be
  able to subscribe to. The allow-list is also what M3's declarative view
  contributions replace; recorded as a deviation with that sentence.
- **Pane chrome does not exist** — `TerminalPane` renders one bare `<div>`. The
  indicator is a new chrome element: a dot + industrial micro-label (`WORKING`,
  `BLOCKED`) in the state's accent colour. Flock rule 8 keeps plain dots as the
  micro fallback, so this is rule-compliant now and the sheep silhouette lands
  when the art does — **M2 is not blocked on artwork**. Fixed-height row (rule 9;
  v1 reverted exactly that), and written **structurally unconditional**: a
  `_ConditionalContent`-shaped wrapper re-runs the attach effect, which here costs
  the xterm and its scrollback rather than the pty.
- **Dock badge** from `attention.count()`; **banner/chime** from `decide()` (D7).
  Both live in `main` — legal there (`boundary/app-main` denies only React, OS
  APIs and the DOM) — and the plan says so explicitly because `boundaries.js`
  calls platform "the ONLY place OS APIs appear" and `app.dock`/`Notification` are
  neither.
- **`pnpm smoke:m2`** against the real Electron binary: boot → create sessions →
  POST a hook sequence over `hooks.sock` with `curl` (a stub agent — the wire is
  what is under test) → assert the indicator changed, the badge moved, and that a
  `Stop` on a **focused** pane lands `idle` while one on an **unfocused** pane
  lands `needsCheck`. Focused-vs-unfocused, *not* app blur: the presence handlers
  are registered after the smoke's own `return` in `main/index.ts`, so presence is
  frozen at `appActive: true` in a smoke run, and `isFrontPane` reads
  `layout.focused(root)`. `runSmoke`'s options type widens to carry the layout,
  attention and viewing handles.
- **Unit tests cannot tell you a wire exists** — v1's LAN bug was every unit
  correct and `acceptBridged` a silent no-op on an optional chain.
- Plus one **manual verification with a real `claude`**, which no smoke can stand
  in for, reported honestly.

## Out of scope for M2

Tasks, worktrees, `TaskRootSynth`, the composer, the sidebar tree (M3). Workbench,
remote, nudges, onboarding, packaging. `ProcessAPI` and `SecretStore`
implementations. The `onView:` activation event. Presence sensing — `away` stays a
`decide()` parameter that main passes `false`, per §7d, which dates that work to
post-M4.

**The §7c headless seam (`complete`/`stream`) is out of scope, whole. This
deviates from the handoff's step 4**, which lists it as M2 work — and the handoff
is the third document, alongside core-design §7 (whose M2 line omits the seam) and
§7c (which decided its shape). Flagged loudly because a descope is the reader's to
accept, not the executor's to make quietly.

The earlier draft phased it last and split it "`complete` ships, `stream` may
slip". That split is in the wrong place. Three reasons, in the order they
discriminate:

- **Neither verb has a vehicle.** `agents-core` runs in the utility process, where
  `boundaries.js` denies `child_process` and `node-pty`, and `ProcessAPI` is
  unimplemented until M3. There is no way to start `claude -p` at all — so the
  blocker was never specific to streaming.
- **A vehicle is not a bullet.** Even granting a main-side exec command,
  `complete` would ride the child→host call path, whose deadline is
  `CHILD_CALL_TIMEOUT_MS = 15_000` (`ext-host/runtime.ts`). A real `claude -p`
  routinely runs 30s–2min, so it needs per-call timeout overrides or a
  start/notify/collect job protocol — new wire surface either way, deserving its
  own design pass rather than a phase.
- **It would ship an API with no consumer**, which §7's proving ground forbids:
  built-ins are *required to consume* proposed APIs, and an API nobody calls is
  the "looks wired, does nothing" shape this codebase exists to refuse. §7c's own
  motivating consumer does not plausibly exist before M3's orchestrator.

**The shape is not reopened, only the date.** §7c's decisions — vendor-blind,
normalized union plus `raw` passthrough, declared per-kind capabilities — stand
untouched. Earliest honest landing is **M3**, where `ProcessAPI.exec` gives
`complete` a vehicle and `tasks` gives it a consumer; `stream` needs its own
frame-family design regardless. The M2 ADR records this deviation against the
handoff by name.

One consequence to clean up rather than leave drifting: the `agents` permission's
comment in `packages/sdk/src/permission.ts` says it is listed "ahead of its **M2**
implementation". That milestone just moved, so the comment is now stale in exactly
the way this repo documents hunting — it loses the milestone in the ADR commit.

**Resume is deliberately half a feature, and the half is named.** Layout
persistence is unwired on purpose (`main/index.ts` says why: a restored tree would
make the smokes non-deterministic), so there is **nothing to restore into**. M2
captures `resumeSessionID` and builds the seeding seam; the restore that consumes
it lands with layout persistence in M3. Saying so here stops an executor building
a restore path with no caller.
