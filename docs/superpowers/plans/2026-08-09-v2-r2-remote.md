# R2 — the remote library Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans.

**Goal:** A paired device drives a real session on this Mac, over TLS, through
the same attachment protocol the renderer uses — so "the phone is another client"
is a fact about the architecture rather than a claim about it.

**Design:** [`../specs/2026-08-09-v2-attachment-and-remote-design.md`](../specs/2026-08-09-v2-attachment-and-remote-design.md) §4 R2
**Depends on:** R0 (a screen on attach), R1 (a framed protocol with no privileged consumer).

## Global Constraints

- `env -u NODE_OPTIONS` on every Electron command.
- `boundaries.js` IS the architecture diagram.
- Failures are typed `Result` values, never throws.
- Bytes, not strings, on the pty path.

## Probe findings (measured 2026-08-09, before planning)

- **openssl → PEM → Node TLS works, and the pin format survives.** A self-signed
  RSA-2048 cert mints in **69 ms**; Node's TLS takes the PEM key/cert directly.
  The pin is **SHA-256 over the whole certificate DER**, which is what
  `SecCertificateCopyData` (v1), `cert.encoded` (Android) and
  `X509Certificate.raw` (here) all produce — so the phone's existing pinning code
  needs no change.
- **A wrong pin is refused by us, not by the stack.** There is no CA, so
  `rejectUnauthorized: false` plus an explicit fingerprint comparison IS the
  verification. That is the whole trust model and it has to be written out.
- v1's identity traps (p12 import, RSA-not-EC because an EC p12 *crashes*
  `SecPKCS12Import`, a non-empty passphrase because empty is `-25293`) are
  Security.framework problems. None of them exist here. **Do not port them.**

## D4 — where the remote server lives

**Decided: the DATA path is served by `shepherdd`; the CONTROL path is served by
the app.** A device holds two connections, which is v1's shape (one control
connection + one data connection per pane) arriving for a better reason.

R1 built `SessionServer` against a `Connection` interface rather than a socket,
so a TLS-terminated connection is a second implementation of that interface — not
a change to the server, and not a proxy. The phone therefore attaches to the
*same* `SessionServer` the Mac's renderer does. That is the strongest available
form of "the phone is just another client for the same pty": there is one server,
one fanout, one mirror, and neither client is privileged.

Control is different in kind. Agent state, the task list, attention and the
layout live in **extensions, in the app** — the daemon deliberately knows nothing
about them (R1 kept `onWillCreate` in main for exactly this reason). Serving them
from the daemon would mean the daemon loads extensions, which is a much larger
thing than a daemon that owns ptys.

**The split has a property worth stating, because it is the point rather than a
consequence:** restarting the app drops the phone's *control* channel and leaves
its *terminal* alone. You update Shepherd, the sidebar on your phone goes
briefly stale, and the agent you were watching keeps running and keeps streaming.
A single-connection design cannot express that.

## D5 — what a device may do

Every transport into the kernel is the same command registry, and the envelope
already carries `caller.kind === 'device'` (§4.3). R2 does **not** invent a
second authorization path: a device's invocations go through the dispatcher like
anything else, and the grant is per-device.

v1's answer — drive existing terminals, no structural mutation — is kept as the
*default grant*, not as a hardcoded limit. The difference matters: v1 could not
express "this device may also close a pane", and here that is a grant entry.

### Task 1: Pairing, as a pure state machine

**Files:** create `v2/packages/remote/src/pairing.ts` + `.test.ts`

Everything decidable without a socket, so it can be asserted without one:

- [ ] A **6-digit code**: minted on demand, one device, **5 minutes**, **3
      attempts**. Expiry and attempt-exhaustion are separate refusals with
      separate messages — "wrong code" and "too many tries" are different things
      to a person holding a phone.
- [ ] **SAS digits** over the certificate DER, for the compare-the-digits
      confirmation. v1's finding is normative: the host shows **three** candidate
      digit groups and the user picks the client's, because an Allow button gets
      pressed without looking.
- [ ] The **handshake decision function**: `(hello, devices, code) → accept |
      needsApproval | reject`, with a reason on every refusal.
- [ ] A **paired device** carries an id, a name, a per-device secret, the pin it
      learned, and when it was last seen. The secret — not the code — is what a
      returning device presents.
- [ ] Tests: an expired code; a third wrong attempt; a device that pairs, is
      revoked, and comes back; a `pinVerified` client that skips the digits
      (v1's `ControlMessage.Hello.pinVerified`, kept).
- [ ] Commit.

### Task 2: Identity and the TLS endpoint

**Files:** create `v2/packages/remote/src/identity.ts`, `endpoint.ts` + tests;
modify `packages/platform/darwin/src/exec.ts` if minting needs a new verb

- [ ] Mint once, at `<support>/remote-identity/{key,cert}.pem`, mode **0600**,
      through the platform's `ProcessAPI` — never `child_process` here.
- [ ] **Re-minting is a breaking act**: every paired device pinned the old cert.
      Reset must therefore also drop every pairing, in one function, so the two
      cannot be done separately.
- [ ] `Endpoint` is the transport seam: `{ listen(onConnection): Promise<Result<Listening, string>> }`.
      Core ships **loopback TCP** only — `remote-lan` and `remote-tailscale` are
      extensions, which is the whole reason this is an interface.
- [ ] Tests: the pin is stable across a reload; a wrong pin is refused; the key
      file is 0600.
- [ ] Commit.

### Task 3: The remote server (control)

**Files:** create `v2/packages/remote/src/server.ts` + test

- [ ] Accepts a framed connection, runs the handshake, and on success issues a
      **session nonce**.
- [ ] Answers a **snapshot** built from v2's nouns — sessions, their agent state,
      the layout tree — and pushes changes. NOT v1's `WorkspaceTree`: this is the
      re-mapping D3 asks for.
- [ ] Client→host invocations go through the **command registry** with
      `caller.kind === 'device'`. No second dispatch path (§Bad-2's whole point).
- [ ] Revoking a device drops its live connections immediately.
- [ ] Commit.

### Task 4: The data path is the daemon's

**Files:** modify `v2/packages/daemon/src/main.ts`; create the TLS `Connection`

- [ ] A data connection presents the **session nonce** the control channel
      issued. No nonce, no stream — a raw pty must not be reachable without a
      live, approved control session (v1's rule, kept).
- [ ] It then becomes an ordinary `Connection` handed to `SessionServer`. **No
      new session code.** If this task needs any, the R1 interface was wrong.
- [ ] The device's viewport is registered per connection, so R0's arbitration
      already does the right thing and a phone that goes away stops constraining
      the Mac.
- [ ] Commit.

### Task 5: The loopback E2E

**Files:** create `v2/packages/remote/src/e2e.test.ts`

The gate, and it needs no phone and no tailnet:

- [ ] Two instances over `127.0.0.1`: pair with a code, approve, attach, type,
      see the echo.
- [ ] **Drop the link mid-stream, reconnect, and require a correct repaint** —
      which is R0's snapshot doing the work, and the case v1 lists as its accepted
      limitation.
- [ ] A second device attaching does not evict the first (v1 allowed one viewer;
      R0's arbitration means we no longer have to).
- [ ] Commit.

## Done when

A paired client over loopback drives a real session end to end, survives a
reconnect with a correct screen, and reaches the kernel only through the command
registry as `caller.kind === 'device'`.

## Explicitly NOT in R2

- **The phone.** R3 ports the Android client onto this.
- **LAN / tailnet endpoints.** Extensions, by decision — core ships loopback so
  the seam has a consumer without shipping a discovery stack.
- **Push notifications.** They ride the control channel's state events, and
  belong with presence (§7d), not with the transport.

## Follow-ups, recorded during the first device run

### The device file should be in the store

`<support>/remote-devices.json` is a **second persistence mechanism**, and this
repo has exactly one on purpose (ADR 0021: `node:sqlite`, stdlib, no native build
against Electron's ABI). It exists because the daemon has no userData and both
processes must read the same pairings — but that is an argument for the daemon
opening the store, not for inventing a file beside it.

Why it is worth fixing rather than leaving: two mechanisms means two migration
stories, two shapes to validate, two things to back up, and a JSON file with no
schema version at the exact place a future field will need one. The atomic
rename and the shape check in `devices.ts` are re-implementing, badly, what the
store already does.

The fix is small: point both processes at the same SQLite file (it handles
multi-process access) and delete `devices.ts`. It was not done during the live
run because the run was about proving the path, and swapping the persistence
underneath a device that had just paired would have made a failure ambiguous.

### The control port must be stable

The OS picks it (`port: 0`), so it changes on every app launch — and a phone
stores the port it paired with. Restart Shepherd and the phone says "connecting"
forever, having been given an address that is now somebody else's.

The daemon does not have this problem by accident: it outlives the app, so its
port stays put for as long as the pairing does. The control port needs the same
property deliberately — remember the chosen port and re-bind it, falling back to
a fresh one only when it is taken.
