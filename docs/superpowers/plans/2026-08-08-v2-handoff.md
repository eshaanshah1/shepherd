## Known gaps, honestly

- **No `shepherd` shim on PATH.** The CLI runs via `node packages/cli/src/main.ts`.
  v1's `CLIShim` (create-or-repair, never replace) belongs with packaging.
- **No plugin installer.** `~/.claude/skills/shepherd-v2` is a hand-made symlink.
  ADR 0005's five-case classification is unbuilt.
- **A handler failure's message is doubled** — wrapped once in the child and
  again in main. Cosmetic, pre-existing.
- **`registerStatusItem` and panel views refuse**, naming a later milestone.
  Panel views stay the decided answer for the **app-like** case (the workbench,
  which brings its own editor) — ADR 0033 records why the composer is not one.
- **The in-proc UI table is static** (`renderer/extension-ui.ts`), so a
  third-party extension has no way to contribute a component yet. §7's
  graduation order, deliberately: a runtime loader is the next piece, not this
  seam.
- **No repo history for the picker.** The default suggestion provider answers
  with the repos of recent tasks, which is thin on a fresh install and empty on
  first run — typing a path is the primary entry, a suggestion the accelerator.
  Usage-and-recency ranking wants history nothing records yet.
- **The interactive trust dialog** for a generated `settings.json` is unmeasured
  (ADR 0029's open question). Headless, with no trust record, it is honoured.

## What M3 taught, that the next milestone should keep doing

**Three gates were passing without checking anything**, and each was found by
mutation-testing rather than by reading:

- `extensions/tasks` was missing from the root tsconfig references, so
  `pnpm typecheck` never looked at it — a planted type error produced no output.
- A deadline test used `Promise.race` against an already-resolved sentinel, which
  wins by one microtask regardless; it passed with the change reverted.
- A round-trip comparison passed with **both sides empty**, because the worktree
  had never been provisioned.

**The composer's own live run kept the streak.** Its first run failed on a
hardcoded repo name in the smoke: the CLI *supplies* a repo's name and the
picker *derives* it from the path, so the composed task's worktree is at the
path's basename, not `api/`. The component's first unit test found a second one
— a suggestion provider answering something that is not an array took the whole
form down with a `TypeError`, because a cast is not a check and a third-party
provider is exactly what D5 invites.

**The composer's repo picker is now an inline `#repo` mention** (2026-08-10,
[design](../specs/2026-08-10-inline-repo-mention-picker-design.md)). `#` anywhere
in the brief opens a caret-anchored picker, ⏎ inserts an atomic `#name` pill into
the text, and the task's scope is **read back out of the pills** — the sentence is
the source of truth, so there is no selection array to disagree with what is on
screen. The separate repo `Field`, its ghost-text layer and the chip row are gone;
`PromptField` already had the atomic-pill and `data-token` machinery, so no
rich-text dependency was added, and `tasks.suggestRepos` needed **no change** (a
bare word is answered from history, anything with a `/` from disk, which is how
path entry survived inside one trigger).

Three defects in it were invisible to 2,000 green tests and obvious on screen, all
three in the same family — CSS and stacking, which no assertion about markup
reaches. The popover drew its border from `--sh-line`, which `.sh-ui-composer`
re-declares to **transparent** for its whole subtree; it was painted
`--sh-surface-raised`, which is the card's **own** fill, so it had no contrast
either (the role ladder stops at `surfaceRaised` — **FINDING: it needs a
`surfaceOverlay`**, and this is also why rule 2's no-shadow argument was reversed
here: there is no step left to spend above a raised card); and `.sh-ui-modal`
carries `overflow: auto` **with** `transform: translateX(-50%)`, so the transform
makes it the containing block for even a `position: fixed` child and the overflow
then clips it — the panel is portalled to the body for that reason. The first two
are now pinned by `composer-picker.css.test.ts`, which needed `css: true` on
`packages/app`'s vitest config and asserts the stylesheet loaded before asserting
anything about it. **If you add a bordered thing inside the composer, re-declare
`--sh-line` or it draws nothing.**

**Driving the real thing found what unit tests could not**: the CLI's first run
turned up a wrong route, a kernel-level disagreement about "no arguments"
(`s.nothing()` rejected `{}` while an all-optional `s.object` rejects absent, so
no generic client could speak to both), and my own fix for the first of those
breaking the second. The view mechanism's first run turned up three more.

**Probe before planning still pays.** Probe 2 ran v1's own algorithms against
fixtures and found a **silent bug in `WorktreeService`** — a branch existing only
on a remote gets the wrong content under the right name with a wrong upstream,
exit 0, first symptom a push failing much later — which a faithful port would
have carried into v2's foundation.

## R4: another member's terminal, on this Mac (2026-08-11)

**Built, and the live two-Mac gate is the one thing still owed.** Design and every
deviation from it:
[`../specs/2026-08-11-shared-session-attach-design.md`](../specs/2026-08-11-shared-session-attach-design.md).

Clicking a task row that belongs to another member of the shep-net opens a
terminal HERE showing that member's live session. Both machines stream, both can
type, and the pty's size is arbitrated between them. **B's window does not move**,
which is the part that decided the shape: a row's `command` is a GESTURE
(`tasks.reveal` opens a root and switches the window), so sending it across the
net moved the other Mac's screen and left this one blank.

Five things to know before touching any of it:

- **A row may now declare `presents` beside `command`** — a verb that ANSWERS what
  the row stands for and performs nothing (`tasks.presentation` is
  `tasks.reveal`'s liveness check minus the `layout.openRoot`). A remote row goes
  through that verb or does nothing at all; it must never fall back to `command`.
  A verb rather than a field on the row because a row is drawn once and clicked
  later, and `tasks.reveal` already carries the scar of presenting a recorded
  session id nothing had checked.
- **A session id qualified with a member is another member's session** —
  `mac-b∷01H…`, the same bookkeeping `remote-views.ts` does for view types.
  `SessionRouter` puts every machine behind one `SessionHostLike`, so
  `SessionBridge`, the IPC layer, `pane-sessions`, `terminal-pane` and xterm learn
  nothing. **A `kill` of a qualified id DETACHES**: this Mac is a viewer, and
  closing a pane here must not stop work over there. Its negative control is kept
  pointing the other way round, because the assertion passes just as happily
  against a router that kills nothing at all.
- **Every viewer now DECLARES a viewport; nothing calls `resize` from a pane.**
  `host.resize` never touched the viewport map, so a pane reporting its window as
  authoritative fought the arbitration `core/session/viewport.ts` was written for
  — and could not be seen by it. `resize` is for programmatic callers only now. A
  pane must also WITHDRAW its viewport when it stops watching, on all three paths
  (`suspend`, `release`, `dispose`): one left behind keeps every other viewer of
  that pty letterboxed with nothing on screen to explain it.
- **A pane can be born already bound to a session** (`PaneSeed.session`, applied
  before the store notifies). The renderer decides to START a pty by looking for a
  binding in the snapshot it was handed, so a pane announced unbound is a pane it
  opens a local shell in — and binding a moment later leaves a stray shell beside
  the terminal you asked for. This is the trap to remember for anything else that
  wants a pane showing something that already exists.
- **A member advertises NOTHING when its own endpoint is loopback**
  (`selfAdvertisement`, the mirror of `rosterAddress`). This was a live defect: a
  Mac launched without `--shepherd-remote=wifi` served control on 127.0.0.1 and
  still advertised its port, so every other member held a roster entry with a
  name, a port and a recent timestamp that could never be dialled.

Also landed: **rows fade and slide in** rather than appearing by a wholesale list
swap (opacity and transform only — never height, and never on the first list), and
**the composer picks which machine a task starts on** (absent when there is only
one; `tasks.create` forwards itself through `remote.at` rather than keeping a local
record about work on another disk).

**What is owed:** two Macs in one net, `pnpm ship --dev` on both, launched with
`--shepherd-remote=wifi` — open a row belonging to the other, type on both, then
resize the smaller window and watch the larger letterbox. This Mac has LEFT the
net (`remote.leaveNet`), so re-join from the other machine first. A green unit
suite is not a working app, and this repo has the scars.

**Still open, deliberately:** a listener binds one interface at startup and
advertises it forever (the work Mac handed out its ethernet address after the
cable was unplugged). It needs address re-resolution on a network change. And
capability scopes remain the one place t3code is ahead — membership still grants
entry AND everything, and the data path a member reaches is the phone's, unchanged.

## Settings (ADR 0040) — landed 2026-08-11

⌘, takes over the window. The frame is the shell's (nav, search, back, Esc); the
pages are contributed, declared as `contributes.settings` in a manifest and held by
the kernel — so the screen lists every extension's settings with **zero extensions
activated**, and opening one page activates one extension through the
`choicesFrom` command it names. Values live in the one store, and only when they
differ from a declared default.

The two comments that asked for this are now resolved rather than restated:
`agents-core`'s "one key rather than a settings system, because v2 has none" is two
nullable enum keys whose options come from a command (so the models arrive as data
from the vendor and no vendor is named), and `worktree-hook`'s "a view of its own
ONLY because v2 has no settings surface yet" is a component page — which is what
proves the escape hatch is a mechanism rather than a paragraph. **Light mode** came
with it: `shepherd.theme` paints the chrome and re-themes every live xterm in
place, no relaunch and no pane rebuilt.

Five things to know before touching any of it:

- **Whether the screen is open is MAIN's answer** (`window.settings`), not the
  renderer's, because the same value feeds `presence.overlay` — so the ⌘, menu
  item, the palette entry, `shepherd raw window.settings` and Esc all move one
  variable, and ADR 0020's single predicate accounts for a takeover. The
  composition is the pure `presenceFor()` precisely so that can be asserted without
  Electron; its negative control has been run.
- **A setting key must sit in the declaring extension's namespace**, derived by the
  host from the manifest id. An extension reads its own keys plus `shepherd.*` and
  nothing else — a cross-extension read is how D11 breaks quietly.
- **`contributionsOf` in `core/extensions/manifest.ts` drops what it does not
  name.** `contributes.settings` passed the schema, reached the registry as
  nothing, and `agents-core` refused to activate over a setting it had declared.
  Add a contribution kind there too, or it silently does not exist.
- **`packages/app/src/shared/**` may not import a runtime value.** The sandboxed
  preload loads that barrel: a `CORE_NAMESPACE` import there failed the preload
  script with `module not found` and took the window with it. `THEME_KEY` is a
  literal pinned by a test for that reason.
- **A component settings page has no view type**, so D14 attribution goes through
  `settings.invoke(page, command)`, which resolves the page's owner from the
  registry and invokes as that extension — never as the user.

**What is owed:** open ⌘, in a shipped build and click through both contributed
pages, then change the quick-tier model in the screen and read it back with
`shepherd agent quick-model` (and the reverse — the screen follows a CLI write,
because the push comes off the bus rather than off the write).

**Still open, deliberately:** the update checker's General section (v1's is five
files plus a design doc), a human-editable `settings.json` (a watcher, precedence
and parse-error UI — later, as another writer to the API that exists), per-scope
values, and component pages for third parties, which wait on a runtime UI loader
the way every ADR 0033 consumer does.

## GitHub PR tracking (ADR 0044) — landed 2026-08-14

**A task's pull requests, on its row and in a tab of its own.** Built from a
design in `Shepherd Git.dc.html` (turn 7): a review tab with a home page listing
every PR of the task, one row each, and a detail page for one PR with `‹ PRs` as
the way back. One PR skips the list entirely — the tab *is* the PR.

**The load-bearing part is not the GitHub client; it is the pane kind.** Every
leaf of the layout tree was a terminal, so there was no place for a surface with
a subject to live. That is ADR 0044:

- **`Pane` may carry a `view`** (`{ type, state }`), persisted like `readOnly` and
  unlike `initialCommand`. `layout.split` and `layout.newTab` accept it, and
  `newTab` grew a `title` because a view pane runs no program and would otherwise
  be called `term`.
- **The renderer never mounts `TerminalPane` for one**, which is the whole
  enforcement — `TerminalPane` attaches on mount and attaching spawns a pty. A
  PR list with a shell behind it would be visible nowhere and killed by nothing.
- **`type` is a REGISTERED VIEW, never a component name.** A pane is persisted,
  so a `view` on disk outlives the process that wrote it; naming a component
  directly would let a persisted record draw arbitrary contributed UI with no
  manifest entry behind it. Two hops, and the second is the gate.
- **`ExtensionPaneProps`** adds `state` and `focused` to `ExtensionViewProps`.
  `focused` is not a nicety: a pane binds keys, and a background one that
  answered them would fight the pane you are looking at.

**`tasks.cardFacts`** is the other new seam, and it is `tasks`' rather than the
kernel's: a provider answers "what else is true of this task" with **at most one**
bounded fact — a glyph name, a short mono label, a token ROLE, a tooltip, a
command. Multiplicity is the provider's problem (three PRs are one glyph whose
tooltip says three), because a task row is a fixed height. It is **synchronous**,
so a provider answers from what it already knows; `tasks.cardFacts.changed` on the
bus is how it says "ask me again". A fact survives onto a shipped row, unlike
every other live field — a merged PR number is the record of what shipped.

**What the extension does and does not do** is in
[`extensions/github/README.md`](../../../v2/extensions/github/README.md). The
one limit worth knowing here: the PAT fallback is inert until `secrets` is
implemented.

**`sessions.write` landed with it**, and it is the kernel's rather than
GitHub's. `SessionHost.paste` had existed since M0 with no way in from outside
main, so an extension with something to say to a running agent had to open a
SECOND agent to say it. Two things about the verb: it **pastes rather than
types** (a typed newline is an Enter press, so multi-line text typed into a TUI
submits its first line and scatters the rest), and `paste` now **brackets iff the
running program asked for it** — read off `TerminalMirror.bracketedPaste`, which
parses the same stream the emulator does. The old "never bracket, the renderer
does it" rule covered the renderer and nothing else; a command caller has no
emulator in the loop.

`github.land` DOES merge — bottom of the stack first, re-reading between each
because merging #1 is what makes #2 mergeable, and stopping at the first refusal
rather than skipping past it. Its button is disabled unless the whole sequence
can go, and it re-checks each PR anyway: the pane drew that button from an answer
up to twenty seconds old.

**Two things measured, both by `smoke:m3` rather than by any unit test:**

- **`secrets.get` THROWS in this build.** It is typed in the SDK and not
  implemented, deliberately — but a token path whose entire job is to answer
  "there is no token" took the extension host down with an unhandled rejection on
  any machine without `gh`. `resolveToken` now treats a throwing secret store as
  an empty one.
- **A background sweep must never fail louder than the thing it swept for.** The
  `void pass()` on the sync timer was the shape that let the above escape.

**What is owed:** run it against a real repo with a real PR. Every test here is
against a fake client and a fake `tasks`, which proves the mapping and the
drawing and cannot prove the query is the one GitHub answers. The specific
unknowns are `mergeStateStatus` behind its preview media type, and whether
`resolvedBy` is populated for a thread an agent closed.

## The PR view, and two bought components (2026-08-14)

The review tab's PR page became **four sub-views** — Conversation, Commits,
Checks, Files — and the diff and file list are now **`@pierre/diffs`** and
**`@pierre/trees`** rather than hand-rolled.

**Why bought:** a diff view is a months-long project (highlighting, hunk
expansion, virtualisation, annotations) and a file tree is another (nesting,
collapse, keyboard traversal, elision). `PatchDiff`'s `lineAnnotations` is
exactly the shape of a review comment on the line it was written about.

**The costs, stated:** `@pierre/diffs` unpacks to ~7 MB, mostly shiki grammars —
worth a look before shipping, given this repo's history with vendored grammar
bundles. `@pierre/trees` renders through **preact into a shadow root**: no second
React reaches the page (the `/react` entries are wrappers), but our tokens reach
it only because custom properties inherit through the boundary, so a descendant
selector from our sheet does nothing. Both are Apache-2.0 and this repo has no
NOTICE file anywhere yet.

**Three things measured rather than reasoned**, and each is a comment in the code:

- **GitHub sends HUNKS, not patches.** Its `patch` field has no `diff --git`
  header, and `PatchDiff` refuses with "Provided patch must contain exactly 1
  file diff". `unifiedPatch` synthesises the header and deliberately does not
  guess `new file mode` from a zero removal count.
- **A thread naming a file is not a thread the diff can show.** Read from
  `pingdotgg/t3code`, which is the same product shape and had already solved it:
  a comment's line may have moved out of the change, so pinning it puts the
  remark against whatever code now occupies that number. `isLineInDiff` splits
  them; the ones it cannot place are listed as `not on this diff`. This is also
  v1's recorded workbench behaviour, arriving twice for the same reason.
- **An effect whose callback prop is a dependency does not terminate** when the
  parent passes an inline arrow and the effect's work causes a render. The Files
  tab's "fetch my patches" ask timed a test out at five seconds. It holds the
  callback in a ref, so correctness is not a rule the three call sites have to
  remember.

**Patches are fetched lazily** — REST `pulls.listFiles` when the Files tab opens,
keyed on `<pr>@<updatedAt>` so a force-push expires the cache exactly when the
answer does. Capped at 100 files with the cap logged, because a silent truncation
reads as "that is all of them".

**What is owed:** still no run against a real GitHub repo. And `github.diff` is
the one call that leaves the single-round-trip design — worth watching if the
Files tab ever gets opened in a loop.

## The app's PATH is now the user's PATH (2026-08-14)

**ADR 0045.** Startup runs the user's login shell once and merges its `PATH` into
`process.env` — `packages/platform/darwin/src/shell-env.ts`, first statement of
`whenReady`.

**Why it was needed even though `STANDARD_BIN_DIRS` existed:** a Finder-launched
`.app` is a child of launchd and inherits `/usr/bin:/bin:/usr/sbin:/sbin`. The
fixed list covers `git` and `gh` and nothing else — every version manager (`mise`,
`asdf`, `nvm`, `volta`, `pyenv`, `rbenv`, `fnm`) puts its shims in a directory that
exists only because a shell profile said so. **Measured on this machine: 28
directories added in 159ms** from a launchd-shaped `PATH`, including
`~/.local/bin`, `/usr/local/go/bin` and `/opt/homebrew/opt/fzf/bin`. Under
`pnpm dev` it correctly adds **zero** — the app was launched from a shell and
already had them.

Read from `pingdotgg/t3code`'s `DesktopShellEnvironment`. Four things copied
because each is a bug avoided:

- **`-ilc`, not `-lc`** — the version-manager line is in `.zshrc`, the INTERACTIVE
  file. A non-interactive login shell reports a `PATH` the user has never seen.
- **`$SHELL`, never a hardcoded bash** — which is v1's own recorded rule arriving
  from the other direction (`bash -lc` reads BASH profiles; a zsh `PATH` is
  invisible). The comment in `exec.ts` that argued against shell probing now says
  what supersedes it.
- **Marker-delimited `printenv`, never a dump of `env`** — profiles print motd,
  fastfetch, warnings, and any of it can look like `KEY=value`. With `|| true`,
  because a profile that set `set -e` would end the script at the first unset name.
- **Merge, never replace** — a profile that overwrote `PATH` instead of appending
  would otherwise take away directories that were working a moment ago.

**Only two names are harvested**, `PATH` and `SSH_AUTH_SOCK`, and the second only
fills in when launchd supplied none. `shell.ts` is the counterweight and worth
reading beside it: that file exists to STRIP inherited variables (dead proxies,
another agent's session ids, forty `npm_*` keys), and harvesting is the same door
in the other direction.

**It is awaited, and first, for three orderings that are each a real bug:**
`remote.serve` shells out to `openssl`; the daemon is spawned lazily and inherits
`process.env` at that moment; and `resolveProgram` **caches**, so anything resolved
under launchd's `PATH` would outlive the reason it was wrong. The install drops
that cache but cannot undo a spawn that already happened. Cost is bounded at 3s and
the measured `ms` is logged.

**What it removed:** `token.ts`'s hardcoded `CHILD_PATH` — the last PATH list
outside `platform/darwin`. An extension naming `env` in `ExecOptions` replaces the
child's environment, so "know where tools live" had already become a rule
extension authors have to remember. A test now asserts `github` names no `PATH`.

**Still owed, unchanged:** the Secrets settings page, and nothing here has run
against a real GitHub repo.
