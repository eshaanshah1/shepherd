# v2 M3 — implementation plan (tasks)

**Status: DRAFT — probes in flight, not yet reviewed.** Do not execute until the
feasibility review and the advisor pass are recorded at the bottom.

M3 is where **dogfooding begins**, which changes what "done" means: every earlier
milestone was proved by a smoke, and M3 is proved by the user creating a real task
across real repos and an orchestrator working inside it. The smoke is necessary and
not sufficient.

Sources: sketch §4 (the task model) / §7b (Scratch, SQLite, CLI-first) / §7c (the
headless seam and its `agents` permission); core-design §4.6 (`ProcessAPI`), §4.7
(extension points, "extensions are platforms"), §5.3 (`tasks` as specified), §7
(M3's line); architecture review's Rebuild checklist item 4 (one `runGit`).

## What M3 must deliver (core-design §7's line, unpacked)

1. The **task store** — SQLite, schema-versioned, the only authority. The task
   folder is derived and must be reconstructible from the store alone.
2. **`TaskRootSynth`** — pure: repos + brief → the generated `CLAUDE.md` and the
   `.claude/` aggregation plan, conflicts flagged.
3. **Worktree-per-repo provisioning** — v1's `WorktreeService` semantics through
   `gitWrite`, one worktree per repo under `~/.shepherd/tasks/<slug>/`.
4. **The ⌘T composer** — title, brief, repo fuzzy-picker, worktree/branch, and the
   orchestrator auto-start.
5. **Scratch** — ⌘T with everything default is a loose shell in a persistent
   section; cwd + title only, never a resumed agent.
6. **spawn / archive / restore** — `tasks.spawn` callable by an agent scoped to its
   own task; archive is v1's two-commit format per repo; restore round-trips.
7. **The sidebar tree** — tasks grouped by state, per-task session dots riding
   attention, as an **extension view contribution** (if it needs a core special
   case, the view model is wrong — sketch §2b).
8. **The skill + CLI verbs** — CLI-first (§7b): the `shepherd` CLI plus a skill
   teaching orchestrators when to use a harness subagent and when to use
   `tasks.spawn`.

Plus the two things M2 deferred *into* M3 by name:

9. **`ProcessAPI`** — the vehicle §7c's headless seam was missing, and Rebuild
   checklist item 4's one `runGit` with the structural `gitRead`/`gitWrite` split.
10. **Layout persistence** — deliberately unwired since M0; resume needs it.

## Probes

### Probe 1 — what Claude Code actually discovers at a generated task root

Claude Code 2.1.224, ~20 headless sessions against purpose-built roots, evidence in
`probe-claude/EVIDENCE.txt`. This is the probe the whole synthesis design rests on,
and it moved three things.

| measured | result |
|---|---|
| `CLAUDE.md` at cwd | loaded at session start |
| a **nested** repo's `CLAUDE.md` | **not** loaded at start — lazily injected once a file in that subtree is touched |
| `.claude/skills/<name>` as a symlink, and `.claude/skills` itself as a symlink | **both** discovered *and* executable; no observable difference from a real directory |
| `.claude/agents/<name>.md` as a symlink, and a symlinked agents dir | both discovered and spawnable |
| `.claude/settings.json` at cwd, incl. as a symlink | honoured — `env` and a `SessionStart` hook both fired |
| a **nested** repo's `.claude/` | **skills** load lazily on subtree access; **agents and settings.json are never loaded at all** |
| ancestor directories | Claude walks **up** from cwd for `.claude/skills` and `CLAUDE.md` — found from **three** levels up |
| a non-git cwd | nothing degrades; task roots need not be repos |

**The four consequences, each traceable to a row above:**

1. **Aggregation is required, not a convenience.** A worktree's own `.claude/agents`
   and `.claude/settings.json` are *never* seen from the task root. Skills would
   half-work without synthesis (lazily, after the agent happens to touch that
   subtree); agents and settings would silently not exist. `TaskRootSynth` is
   load-bearing for exactly the reason §4 claimed, now measured.
2. **`~/.shepherd/tasks/` and `~/.shepherd/` must stay free of `.claude/` and
   `CLAUDE.md`** — ancestors leak into every task root below them. Nothing in the
   design proposed putting one there, which is precisely why this needs writing
   down: it is a trap that costs nothing to avoid and is invisible when sprung.
   (The same mechanism read the other way is a feature: a deliberate `.claude/` at
   `~/.shepherd/tasks/` would share config across every task.)
3. **Name collisions resolve in the filesystem, silently, last-write-wins.** Two
   repos each contributing a `deploy` skill do not conflict in Claude Code — one
   symlink simply overwrites the other. So "conflicts flagged" (§4) is not a nicety:
   `TaskRootSynth` must resolve them deterministically (namespace by repo) *and*
   report them, because the failure mode otherwise is an agent silently running the
   wrong repo's skill.
4. **Per-entry symlinks, not a symlinked directory.** Both work identically, so the
   tiebreaker is that only per-entry aggregation can merge N repos into one
   namespace — which is the whole job.

The probe flagged one unknown as M3's highest risk: every session it ran inherited
this machine's global `bypassPermissions`, so it could not tell "a generated
`settings.json` is honoured" from "nothing is gated here". If a generated
`settings.json` needed a trust the user never grants, aggregated settings would be
dead on arrival everywhere but this machine.

**Re-probed directly, and it is mostly answered.** A fresh directory, a generated
`.claude/settings.json` carrying an `env` entry and a `SessionStart` hook, run with
an explicit `--permission-mode default`, and **no trust record for that directory
in `~/.claude.json`** (checked after the run — still none):

```
$ claude -p --permission-mode default 'Reply with just: ok'
ok
$ cat hook.log
fired-9931
```

So project settings apply with no trust record and no bypass. What remains
unverified is narrower and worth stating exactly: whether an **interactive** first
run in a brand-new task root shows a trust dialog before honouring them. That is a
one-time-per-task prompt at worst, not a dead feature — a UX cost to confirm during
the first live run, not a blocker to design around.

### Probe 2 — multi-repo worktree mechanics, and v1's semantics under measurement

git 2.50.1 (Apple Git-155), APFS. Scripts in `probe-worktree/`. It ran v1's
`WorktreeService` and `WorktreeArchive` algorithms verbatim against fixtures rather
than reading them, which is why it found things reading them did not.

**It found a silent bug in v1 that must not be ported.** v1's `branchExists` checks
`refs/heads/` only. For a branch that exists **only on origin**, that check fails,
so v1 takes the `-b <name> origin/<default>` path — and git happily exits 0. The
worktree then holds *origin's default branch's content* under the right branch
name, with an upstream pointing at the wrong branch. Nothing errors. The first
symptom is a `git push` that fails much later with `fatal: The upstream branch of
your current branch does not match the name of your current branch`. So branch
resolution is **three** steps here — `refs/heads/<n>`, then `refs/remotes/*/<n>`,
then create — not v1's two.

**A second v1 rule fails outright and is not portable**: v1 runs `git fetch origin`
as a *precondition* and aborts if it fails. Measured, that makes a repo with no
remote impossible to use at all (`fatal: 'origin' does not appear to be a git
repository`), and its last-resort `-b x origin/main` is an invalid ref in that repo.
Offline is the same story. Fetch must be opportunistic, with a local base ref as the
fallback — never the literal string `origin/main`.

**Timing, which corrects D12's reasoning rather than its conclusion:**

| | measured |
|---|---|
| `worktree add`, real repo (1036 files, 34M) | **0.16s** |
| same, synthetic 20k-file / 80M repo | 2.03s |
| a real network `ls-remote` (proxy for the fetch) | **2.51s** |

Checkout is cheap; **the network is the entire latency**. A three-repo task pays
~7.5s before a single file is written. Optimistic provisioning is required — v1's
conclusion, for a different and stronger reason than v1 gave (v1 blamed checkout).

**The archive is better than expected in the place everyone assumes it is worse, and
worse in three places nobody checks.** Run end-to-end on a fixture with staged
edits, unstaged edits, both-on-one-file, staged and unstaged deletions, untracked
files, an untracked file in a new directory, and gitignored files, `git status
--porcelain` before and after is **byte-identical**. **Untracked files survive** —
the classic gap is not present. What is:

- **Gitignored files are silently destroyed** by both `worktree remove` and the
  archive path (`add -A` skips them; `remove --force` then deletes them). `.env`,
  `node_modules`, build output. No warning anywhere.
- **A conflicted worktree cannot be archived at all** — `write-tree` hard-fails
  (`fatal: git-write-tree: error building trees`, exit 128). A task stopped
  mid-merge is exactly the one a user wants to shelve.
- **A detached worktree restores to the wrong commit** — measured: HEAD comes back
  as the *archive* commit, because restore skips `symbolic-ref` when the branch is
  empty.

**Five more constraints, each measured, that the executor must build to:**

- **The path is the identity.** git silently renames the metadata dir on a basename
  collision (a second `alpha` becomes `alpha1`), so nothing may key on it.
- **A branch can be checked out once per repo.** Two tasks touching one repo on one
  branch collide (exit 128). That is a policy decision (per-task branch names), not
  a case for `--force`.
- **Leftovers come in two kinds with different cures**, distinguishable only from
  `worktree list --porcelain`'s `prunable` lines, never from directory existence.
  A non-empty target directory has **no** force flag — `--force` and `--force
  --force` both fail; the only recovery is removing it or choosing another path.
- **Rename is `git worktree repair`, not delete-and-recreate** — repair preserves
  uncommitted *and* untracked work. And **prune-before-repair permanently orphans**
  the directory: repair cannot rescue it afterwards. Reconstruction should use
  `worktree add --force <path> <branch>`, which clears the one stale registration
  without a repo-wide prune that would take siblings with it.
- **Submodule repos break every cheap rule above** — empty-but-*clean* after add
  (needs an explicit `submodule update --init`), `remove` needs `--force`, `move` is
  impossible, and `repair` leaves the submodule broken. Detect `.gitmodules` and
  decide the branch deliberately.

## Decisions taken here, not left to the executor

### D1 — the child→host deadline becomes per-call; `exec` keeps its declared shape

**Measured**: `CHILD_CALL_TIMEOUT_MS = 15_000`
(`packages/app/src/ext-host/runtime.ts:63`), applied as one flat constant to
*every* child→host call at `runtime.ts:396-399`. It exists so a wedged host
produces a timeout rather than a promise nobody settles, and that reason is good.

It is also shorter than things M3 legitimately runs. `git fetch` against a cold
remote is the clear case (v1 runs one before every worktree creation and aborts the
whole operation if it fails); a `worktree add` on a large repo is the plausible
one. Under a flat 15s the extension would be told its provisioning **failed** while
git was still working — and then the worktree appears anyway, which is the worst
version: a false failure with a real side effect.

The handoff read this as "so `exec` needs a job protocol, not a verb". It does not,
and the reason is in the API that is already declared: `ExecOptions.timeoutMs` is
**required** (`api-kernel.ts:117-123`), so the caller has already stated how long
this particular call may take. The transport should honour that number instead of
overriding it with a smaller one it knows nothing about. So:

- `ApiCall` carries a deadline; `#call` uses it, falling back to the 15s constant
  for every call that names none. One small change at one site, and the flat
  default — the property the constant was protecting — survives untouched.
- `exec`/`gitRead`/`gitWrite` land promise-shaped, exactly as core-design §4.6
  declares them. No new protocol, no second way to run a program.

**Two things ride along, and the first is a bug the change would otherwise
create.** The property the constant protects is "a wedged host produces a timeout,
not an unsettled promise" — and with a 10-minute deadline in play, the 15s timer
stops being an acceptable stand-in for a *dead* port. Main's side already knows
this: `ext-host.ts:508` has `#failPending`, settling every outstanding call with
`unavailable` on disconnect. **The child's side has no equivalent** — grepping
`runtime.ts` for a close/disconnect handler finds nothing, so its only escape is
that timer. Raising the deadline without adding the child's `#failPending` turns a
dead main process into a ten-minute hang. So D1 is two edits, not one, and the
second is the load-bearing half.

And a call naming **no** deadline must still time out at 15s — the flat default is
the property being preserved, so it gets a test, and that test gets mutation-tested
(delete the fallback, watch it fail by name).

**Where the runner lives**: `boundaries.js` denies `child_process` to
`extensions/**`, to `packages/app/src/ext-host/**` and to `packages/app/src/shared/**`,
directing OS APIs to `packages/platform/darwin`. The exec runner therefore lands
behind the platform boundary, invoked from main — **not** by widening a boundary
rule. If the executor finds itself editing `boundaries.js` to make `ProcessAPI`
work, that is the signal to stop and report, not to widen.

**§7c's streaming half stays out of M3, deliberately and for a different reason
than last time.** M2 deferred it for want of a vehicle; `ProcessAPI` is that
vehicle, so that argument expires here. The remaining one is that M3 has **no
consumer**: a task's orchestrator and every session `tasks.spawn` creates are
*interactive* sessions in a surface, not `claude -p`. Building the normalized event
union with nothing reading it would fix its shape against zero real use — the exact
mistake §7c's own "a real consumer to shape it" rule warns about for storage. It
lands with its first consumer.

### D1b — an extension cannot resolve a path, and `tasks` is built on one

**Measured**: `boundaries.js` denies `os`/`node:os` to both `extensions/**` and
`packages/app/src/ext-host/**` ("OS APIs live in packages/platform/darwin only").
So `tasks` cannot call `homedir()`, and `~/.shepherd/tasks/<slug>/` — the path the
entire feature is defined in terms of — is not computable where the feature lives.

This is the boundary working, not obstructing: an extension asking the host for a
place to put things is reviewable, testable and relocatable; an extension deriving
one from `$HOME` is none of those. The host therefore hands `tasks` its root, and
the path becomes a host fact that dev/prod isolation already knows how to vary (the
same reason `~/.shepherd/v2-dev/` exists). `TaskRootSynth` stays pure by taking the
root as an argument and never asking where it came from.

### D2 — storage: two settled decisions disagree, and this resolves them by name

Three statements are all on record and they do not compose:

- **§7b**: "Task store is SQLite (**better-sqlite3**, main process, versioned
  migrations)."
- **ADR 0021**: the store is **`node:sqlite`** — better-sqlite3 is a native module
  built against Electron's ABI, and deleting that dependency was the point.
  §5.3's "better-sqlite3" is therefore **stale text**; the plan must not cite it.
- **§7c**: "Storage stays as it is: `KV`… Raw SQL to extensions is a bigger grant
  than it looks (migrations, corruption blast radius) and nothing needs it before
  `tasks` — if M3 proves KV too thin, that is the moment to widen it, with a real
  consumer to shape it."

So the live question is **not** which SQLite: it is settled, it is `node:sqlite`,
and the kernel already owns it (`packages/core/src/storage/store.ts`, one `kv` table,
`migrations.ts:25-44`). The live question is the **API surface `tasks` is handed**.

**Answered: KV as it stands, and nothing widens.** The surface is
`get`/`set`/`delete`/`keys` (`api-kernel.ts:102-107`) — point access plus a
lexicographic key enumeration, with no predicate, no range scan, no secondary
index, no partial update, no cross-key transaction and no change notification. A
task store wants "list tasks by state, ordered". At the scale a human's task list
actually reaches — tens, low hundreds — `keys()` plus an in-memory filter *is* that
query, honestly, with no index for the extension to keep consistent. Widening the
grant to buy an index nobody's data needs would be paying the "bigger grant than it
looks" §7c warns about for a hypothetical.

**Two things constrain the schema, and the first is not obvious.** `ctx.storage` is
a **write-through mirror**: the host ships the extension's *entire namespace* across
the message port in the activate frame (`ext-protocol.ts:225-226`) and it stays
resident in the child. So a task record must stay small — **no transcripts, no
diffs, no file contents in KV, ever**; those are files or they are nothing. And the
mirror's soundness rests on a namespace having exactly one writer
(`ext-protocol.ts:162-168`), which `tasks` satisfies and must keep satisfying.

**The escape hatch stays shut, and this is the thesis, not a detail.**
`SqliteStore.db` exists, commented "escape hatch for core's own tables (**tasks**,
layout). Not exposed to extensions" (`store.ts:52-55`) — and it has **zero callers**.
Taking it would make `tasks` a core-owned table reached through commands, which is
precisely the privileged path the whole ADE bet forbids: `tasks` must consume the
same public API a third party gets, or the substrate claim is hollow (sketch §2b's
absurd bar — an entire GitHub client extension — is unbuildable the moment built-ins
get private tables). If KV genuinely cannot carry tasks, the answer is to widen
**KV**, for everyone, not to hand one built-in the database. That comment is now
stale; the ADR should say so.

**Revisit trigger, stated so it is measured rather than argued:** if archived tasks
accumulate until the activation seed is a real cost, that is the moment to widen —
with a number.

### D3 — layout persistence is already built; it is disabled by one omitted option

**Measured, and it changes the size of this task from a phase to a line.** The
`LayoutStore` implements persistence in full — `PersistedLayout` with a
`schemaVersion`, debounced writes (`store.ts:102`), `#restore` that tolerates a
corrupt tree by warning rather than throwing, a `flush()` that `will-quit` **already
calls** (`index.ts:584`), and tests covering all of it (`store.test.ts:214+`). It is
off because one constructor option is omitted at `index.ts:192-196`, with the reason
in the comment: a restored tree would make the smokes non-deterministic.

**That reason no longer holds, and the fix is to check rather than to argue.** Every
smoke runner already mints a throwaway userData directory per run —
`mkdtempSync(join(tmpdir(), 'shepherd-v2-m2-'))` in `tooling/scripts/smoke-m2.mjs:22`,
the same in `smoke-m1.mjs:25` and `smoke-m0.mjs:39` — and the store lives at
`join(boot.userData, 'store.db')`. A smoke therefore opens an **empty** database and
has nothing to restore. The determinism the comment protects is already provided by
the isolation, one layer down.

So D3 is: **pass the namespace**, delete the stale comment, and add the test that
pins *why* it is safe — a smoke's userData is throwaway — so the next person does
not have to re-derive it. If a smoke does turn non-deterministic, that is a finding
about isolation, not a reason to re-disable persistence.

### D4 — a task's lifecycle state has ONE writer, and `needs-you` is not stored

ADR 0026 established one writer for agent attention and the manifest enforces it.
The same failure is available here twice over: a task's state
(`draft → running → needs-you → review → done/archived`) is partly a **lifecycle**
fact the user or the store owns, and partly a **rollup** of its sessions' live agent
states. Storing the rollup means two writers and a guaranteed disagreement.

So: the store holds the lifecycle (`draft`/`running`/`review`/`done`/`archived`)
and `needs-you` is **derived** at read time from the task's sessions' attention —
never written. A task in the sidebar showing "needs you" is one predicate over data
`agents-core` already owns.

### D5 — the repo picker ships as a consumer of its own extension point

The dogfood rule one level deeper (core-design §4.7). `tasks` defines
`tasks.repoSuggestions`; the usage-and-recency-ranked picker is registered as the
**default provider**, through the same call a third party would make. The canonical
third-party example the user named — auto-picking repos from the prompt text — must
be writable with no change to `tasks`.

Seam discipline: **publish questions, not steps.** A `RepoSuggestionProvider` is
asked "given this input, which repos?" — coarse, and answerable. No step hooks into
the provisioning pipeline: a published seam is a compatibility promise, and
fine-grained hooks would freeze internals and let an extension corrupt invariants
(`StopPolicy`'s ordering guard is the standing example of a decision that must stay
owned by one author).

### D6 — the view-contribution mechanism is a milestone inside the milestone

**This is M3's largest risk and the plan's most important finding.** "The sidebar
tree is an extension contribution" reads like one phase. The seam map says the
mechanism does not exist at any layer:

| what M3's tree needs | today |
|---|---|
| a sidebar, or any dock UI | **absent** — no component, no CSS class, no container |
| `REGIONS` (`main`/`leftDock`/…) | an SDK constant with **zero consumers**; the store has no region concept |
| `ViewAPI.registerViewType` / `registerStatusItem` | **throws** `NotImplementedError` (`ext-host/api.ts:452-460`) |
| a `view.*` wire frame | **absent** from the `ApiCall` union (`ext-protocol.ts:135-178`) |
| a view/tree IPC channel | **absent** (`shared/channels.ts:15-40`) |
| a `TreeDataProvider` consumer | types exported, **imported by nobody** |
| a reader of `manifest.contributes.views` | parsed, validated, then **dropped** |
| anything firing `onView:` | `activateFor` has **zero production callers** — matching logic with no trigger |
| the pushed mirror synchronous `LayoutAPI` reads need | absent, explicitly deferred *to here* (`api.ts:144-148`) |
| the `tasks` extension | `extensions/tasks/` is a **README** |

So P5 is not "draw a tree". It is: the SDK implementation, a wire frame, an IPC
channel, a renderer host for tree data, a region model in a store that has none, an
activation trigger site, and the pushed layout mirror — and only then a tree.

**Consequences for the plan, and they are the reason to find this now:**

1. **The view mechanism gets its own phase, before the task UI.** It is the thing a
   third party needs in order to build the tabbed sidebar / Slack / GitHub-client
   extensions §2b sets as the bar. Building it *as* the task tree would shape it
   around one consumer — the exact mistake §7c's "a real consumer to shape it" rule
   is trying to avoid the other way round.
2. **It is the natural M3/M4 cut line if M3 has to be cut.** Everything through P4
   (store, provisioning, commands, CLI) is usable from the command registry and the
   CLI with no view at all — which is the CLI-first posture §7b already chose. A
   task list that exists and is driveable without a sidebar is a real milestone.
3. **`onView:` and the relay allow-list retire together, or neither does.** Main's
   allow-list (`agent-relay.ts:22-23`, one topic, `AGENT_STATE_TOPIC`) is replaced by
   *declarative contributions*, which do not exist until this lands. Until then the
   allow-list stays and stays honest — it is one constant with its reasoning
   attached, which is the right shape for a placeholder.

**Scope note the executor must respect**: `REGIONS` is where scope creep will enter.
M3 needs one dock to hold one tree. It does not need all five regions, drag-between
regions, or multi-window roots.

### D7 — `TaskRootSynth` emits a plan; a materializer applies it

Purity is the point (it is named as a pure port in core-design §6). It takes repos
+ brief and returns a **description** of the task root — the `CLAUDE.md` text and
the list of links to create, with conflicts flagged — and touches no disk. A
separate materializer performs it. That way the interesting half is table-testable,
including every conflict case, without a filesystem.

Probe 1 fixes three of its rules, which were open before it ran:

- It aggregates **agents and settings**, not just skills. Those are the two a
  worktree's own `.claude/` can never supply.
- It emits **per-entry** symlinks, so N repos merge into one namespace.
- A name collision is **resolved deterministically and reported** — never left to
  the filesystem, where the last link silently wins and the agent runs the wrong
  repo's `deploy`. "Reported" means the composer can show it; a conflict the user
  never hears about is the failure this rule exists to prevent.

The generated `CLAUDE.md` also carries the repo map for a measured reason rather
than a stylistic one: a nested repo's own `CLAUDE.md` is **not** loaded until the
agent touches that subtree, so the root file is the only place the orchestrator can
learn what repos it has before it goes looking.

### D8b — the composer auto-starts the orchestrator, and that is a session verb

Sketch §4: creating a task is a **session-level** verb, not "new tab", because a
task is location-independent — it can be created from a phone, run on the Mac, and
render only on the phone. If M3 implements task creation as "open a tab and start
an agent in it", that property is gone on day one and gets rebuilt later at cost.
The task exists; a *view* of its sessions is a separate, optional thing.

### D9 — Scratch is not a degenerate task

§7b: ⌘T with everything default is a loose shell. Modelling it as a task with zero
repos would drag the whole lifecycle, the folder, and the synthesis into the
zero-ceremony path. Scratch is its own persisted list — cwd + title only, never a
resumed agent (v1's restore discipline) — with promote-to-task as a later verb.

### D9b — an agent caller is denied by construction; nothing mints agent principals

**Verified**: `CommandRegistry`'s grants (`main/index.ts:158-173`) merge
`permissions.grantSet()` with **one** device entry. `grantSet()` "knows only about
extensions" and returns empty `devices`/`agents` maps, and nothing anywhere adds an
agent. `authorize` denies a caller absent from grants — *"is unknown (not registered
as a live principal)"* — and membership is required **even for a command with no
permission**.

So today every `caller.kind === 'agent'` invocation of every command is denied.
§5.3's `tasks.spawn` "callable with `caller.kind === 'agent'`" is not a handler
detail; the principal it needs does not exist. That is a P1 deliverable: agent
principals minted when a session is created and revoked when it exits.

Two things make it smaller than it sounds, both already true in the code:

- The registry reads `grants` **per invocation**, deliberately (`registry.ts:60-65`),
  so live principals need no change to the registry at all.
- **Task scoping stays in `tasks`' handler.** The kernel cannot know which session
  belongs to which task, and teaching it would be exactly the privileged path D2
  refuses. The dispatcher authenticates the *kind*; the extension scopes the
  *subject*.

And one thing to write down rather than build: an agent's `sessionId` claim on the
socket is trusted the way `local-cli`'s device claim is — **reaching the socket is
the trust boundary** (`ingress.ts`). M3 does not add claim verification; it records
that as the model, so the next reader knows it was decided rather than missed.

### D10 — one initial-input seam, and `--resume` enters through it

v1's hardest-won rule here: `takeInitialInput` is **the** `initial_input` seam, and
a composed prompt's launch command wins over the resume line. Two ways to type the
first thing into a session is how you get a resume racing a prompt.

v2 has the same two producers arriving in M3 at once — the composer auto-starts the
orchestrator (§7b), and `claude --resume <id>` restores one (§5.2's "composed-command
seam"). They land as **one** seam with a stated precedence, or they will be two.

### D11 — resume needs a durable key, and there is currently no such thing

The handoff calls resume "half a feature, and the half is named": `resumeSessionID`
is captured in the kind's slot, readable via `claudeCode.resumeTarget`, and nothing
persists it because layout persistence is unwired. That reads like a free
consequence of D3. **It is not, and the seam map shows why it cannot be.**

Three facts that compose into a contradiction:

1. `serialize.ts:17-19` — **the pane id is deliberately not persisted.** "A restored
   pane is a new pane showing an old directory; reusing the id would let a stale
   session id, a stale attention entry or a stale extension record survive a
   relaunch and address it." Restore mints fresh ids, and a test pins it.
2. `pane.ts:11-13` — "anything an extension owns (agent state, attention, **tasks**)
   hangs off the pane id **in that extension's own store**."
3. `initialCommand` is excluded from persistence on purpose, precisely so a relaunch
   does not re-run a command (`serialize.ts:13-15`).

So an extension is told to key its state by pane id, and pane ids do not survive a
restart. Everything `claude-code` knows about a restored pane is therefore
unreachable **by construction** — its resume target is filed under an id that no
longer exists. Both rules are individually right: (1) is what stops stale state
addressing a new pane, and (2) is what keeps `Pane` from growing every extension's
fields. Resume is the first feature that needs to cross them.

**Resolved, and the resolution is that the question was wrong.** The contradiction
is manufactured by the framing "a restored **pane** must reacquire its agent". Drop
that premise and it disappears, because a pane was never the thing that remembers.

Sketch §4, on tasks being location-independent:

> the task list — **not any device's layout** — is the authoritative inventory of
> what's running.

A task's sessions belong to the *task*; a pane is a view that happens to be attached
to one, and on another device there may be no pane at all. So enumerate what could
want a resume target after a restart:

- **A task's session** — the **task store** holds it, beside the session it belongs
  to, keyed by the task id. That key is durable because the store is the authority,
  which is the same reason the folder is allowed to be derived. No layout involved.
- **A Scratch pane** — §7b: "Scratch persists cwd + title only, **never a resumed
  agent**." Decided, and an omission only if you forget it was decided.
- Anything else — does not exist. Every pane in v2 is one or the other.

**So no pane needs a durable key, and neither rule bends.** Pane ids keep being
re-minted, so nothing stale can address a new pane (`serialize.ts:17-19` intact);
extensions keep keying by pane id, because live state is the only kind that does
(`pane.ts:11-13` intact).

What lands instead runs in the opposite direction, and is ordinary: after a restart
the user opens a task's session, a view attaches to it, and the resume target
reaches the new surface through **D10's one initial-input seam**. That is a forward
action with a stated precedence, not a restoration handshake — and it is the same
path a session opened from the phone takes, which is the property §4 asked for.

**What this deletes from M3**: the durable-key design, its GC problem (orphaned
keys for panes that no longer exist), and the one-shot-delivery machinery. What it
adds is a field on a store record that already has to exist.

**The one thing to watch**: this makes `tasks` the owner of a `claude-code` fact.
The task store holds an opaque resume token it never interprets — obtained from
`claudeCode.resumeTarget` and handed back through the same seam. If it ever starts
*reading* that token, `tasks` has learned about a vendor and D2's rule has been
broken from a new direction.

Note what this does *not* need: `initialCommand`'s exclusion stays. Resume is not a
persisted command re-running — it is a restored pane being handed a resume target,
which is D10's one seam with its stated precedence.

### D12 — provisioning is optimistic, because v1 measured that it has to be

ADR 0018: `newWorktreeTab` opens the tab immediately behind a transient
`provisioning` flag and runs git off-main, because `git fetch` + `worktree add` is
seconds of dead UI otherwise. M3 multiplies it by the number of repos in the task —
a three-repo task does that work three times before anything is on screen.

So the task appears immediately, its per-repo worktrees fill in behind a **per-repo**
provisioning state, and a failure removes what it created and says why. The composer
must never block on git.

Probe 2 sized it and moved the reason: `worktree add` on a real repo is **0.16s**,
while one network round-trip is **2.51s**. Checkout is not the cost — the network
is, and it is paid once per repo, so a three-repo task is ~7.5s of nothing. The
provisioning state is therefore per repo, not per task: repos land as they land.

### D12b — the worktree layer is a rewrite of v1's semantics, not a port

The Rebuild checklist says to port `WorktreeArchive` near-verbatim, and M3's line
says "ported `WorktreeService` semantics via `gitWrite`". Probe 2 measured both and
the instruction needs qualifying, because a faithful port carries a silent bug and
an impossible precondition into v2's foundation:

- **Branch resolution is three-way**, not v1's two-way (probe 2). The pure
  resolution — given the local refs, the remote refs and a name, which git
  invocation — is a table-testable function and should be one.
- **Fetch is opportunistic**, never a precondition that can abort provisioning.
- **`refs/heads` collision across tasks** is a policy the store decides, since it is
  the thing that knows another task holds that branch.
- **Archive keeps v1's two-commit shape** — it round-trips byte-identically,
  including untracked files, and that is a genuinely good algorithm worth porting.
  It grows three things it lacks: a gitignored-file **warning** before destruction,
  a refusal-with-a-reason for a conflicted worktree, and the original HEAD sha
  recorded beside the branch so a detached worktree restores where it was.

What ports verbatim is the *shape* (two commits, pinned under
`refs/shepherd/...`, local-only). What gets rewritten is everything that decides
which git command to run.

### D13 — what `smoke:m3` asserts, taken from the handoff's bar verbatim

> M3 passes when a task can be created from the composer with ≥1 repo, its
> worktrees and generated task root exist, an orchestrator agent starts in it, the
> sidebar shows it with live state, and archive/restore round-trips.

That is the smoke, leg for leg. Two properties it inherits from `smoke:m2` and must
not lose: it drives the **real app** over the real wire, and it asserts at least one

## Phases

M3 is the largest milestone so far — it is the one that has to be, since it is the
dogfood gate's supplier. The sequencing rule is M2's: **the pure things first with
their tests, then the affordances they need, then the feature, then the visual, then
the smoke.** Each phase commits green and reports its `deviation:`.

_(Phase contents below are the shape; the exact file list closes with the seam map.)_

### P0 — the pure layer, tests first, no wiring

`TaskRootSynth` (repos + brief → generated `CLAUDE.md` + per-entry symlink plan +
**flagged collisions**), slug derivation and its collision rule (D8), the task
lifecycle vocabulary with `needs-you` absent from it by construction (D4), and the
pure half of per-repo archive. Nothing here imports a host. This is the phase that
can be table-tested exhaustively, so it should carry most of M3's new test count.

### P1 — the kernel affordances M3 needs

The per-call deadline **and** the child's `#failPending` (D1 — the second is the
load-bearing half), and `ProcessAPI` made real. The map names its one legal home:
`packages/platform/darwin/src/` is the **only** production directory `boundaries.js`
permits `child_process` in, imported only from `packages/app/src/main/`, reached
from an extension across the port — which needs a new `process.*` variant in
`ext-protocol.ts`'s `ApiCall` union, a handler in `main/ext-host.ts`, and the
replacement of `createProcess()` at `ext-host/api.ts:635`. The `process.exec`
permission already exists (`permission.ts:14`), so the authorizer needs nothing new.

Plus the host-owned task root path (D1b). Ends with `ProcessAPI` real and nothing
yet calling it from a feature.

### P2 — persistence: the layout, and one initial-input seam

Layout persistence turned on (D3 — one option, one deleted comment, one test that
pins why it is safe), and D10's single initial-input seam with its stated precedence.

**The resume target is not here.** Per D11 it belongs to the task store, so it lands
in P3 with the store — which is also what stops this phase from growing a
durable-key mechanism it turns out nothing needs.

### P3 — the `tasks` extension: store, commands, and its own extension point

The task store on whatever D2 settles, `tasks.create` / `spawn` / `archive` /
`restore` with `caller.kind === 'agent'` scoped to the caller's own task, and
`tasks.repoSuggestions` defined with the usage-ranked picker registered as its
default provider (D5). No UI yet — every verb reachable from the command registry.

### P4 — provisioning: worktrees and the materialized task root

Per-repo worktree creation through `gitWrite`, the materializer applying P0's plan,
optimistic provisioning states (D12), and the failure path that removes what it
created and says why. Archive/restore round-trips here.

### P5 — the view-contribution mechanism, with no task UI in it

Per D6, and deliberately built against a **trivial** consumer (diagnostics
contributing a small tree), not against the task tree. **That consumer must include
an item that changes**: a static tree exercises registration and proves nothing
about change propagation, which is the entire reason the task tree exists. `ViewAPI` implemented, the
`view.*` wire frame, the IPC channel, the renderer's tree host, one dock region, the
`onView:` trigger site, and the pushed layout mirror. Ends with a third-party-shaped
extension putting a list in a dock, and `tasks` not yet involved.

**This is the phase most likely to overrun, and the designated cut line**: if M3
must be shortened, it stops after P4 and this becomes M3b. Everything before it is
usable from the CLI, which is the posture §7b chose anyway.

### P5b — the task UI: composer, tree, Scratch

The ⌘T composer (title, brief, repo picker, worktree/branch), the task tree as a
contribution through P5's mechanism, and Scratch as its own section (D9). If any of
it needs a core special case, **stop and report**: that means P5's view model is
wrong (sketch §2b), and finding it here is the cheap version.

Main's relay allow-list retires here, not in P5 — it is replaced by a real
contribution, so it goes when one exists.

**Name the attention channel, because this bug has been measured twice.** "Per-task
session dots ride attention" must be: dots come from the `attention.changed` topic,
seeded once at activation, and **never read back from the store on receipt**. M2
measured twice that a consumer reading the store when an event arrives sees the
world from *before* the change — the level rides the event (M2 plan D7, ADR 0026).
Stating it here is one paragraph that stops the executor rediscovering it from the
consumer side.

### P6 — the skill and the CLI verbs

**There is no `shepherd` CLI in v2.** Verified: `packages/` is `app`, `core`,
`design-tokens`, `platform`, `sdk` — the control-socket *ingress* is built, the
client is not, and core-design §7 puts the minimal CLI in **M4** while M3's line
says "the skill + CLI verbs". The specs are ambiguous and the plan will not inherit
the ambiguity.

The verbs themselves land in P3 as commands regardless; what is open is what the
skill tells an orchestrator to **type**. Two honest answers:

1. Pull a thin CLI client forward into P6 — HTTP-over-unix, the envelope, the caller
   claim. `SHEPHERD_CONTROL_SOCK` is already injected into every pane.
2. The skill teaches `curl` against the control socket directly — the agent API in
   its ugliest honest form, and a real demonstration that the socket *is* the API.

**Decide before starting P6.** Option 1 is the better product and the larger scope;
option 2 is free and proves the seam. Unnamed, this phase halts on discovery.

CLI-first (§7b) either way: the skill teaches an orchestrator when a harness
subagent is right (cheap, short-lived, invisible) and when `tasks.spawn` is
(tracked, attention-bearing, phone-attachable).

### P7 — `smoke:m3`

D13's bar, leg for leg, driving the real app — including one asserted silence.

### P8 — the ADRs

Everything decided along the way that a future reader would otherwise relitigate.
On current shape that is at least: the per-call deadline and why the flat default
survives; the task-root discovery rules probe 1 measured; one writer for task
state; and whatever D2 settles about storage.

## Out of scope for M3 — named, so they are decisions rather than omissions

- **§7c's headless/streaming seam** (`complete`/`stream`, the normalized event
  union). Deferred a second time, on a new reason: M3 has no consumer for it (D1).
- **Task garbage collection.** Sketch §4 turns v1's 90-day worktree expiry into
  task-GC. Archive/restore must round-trip in M3; *expiring* an archive needs a
  clock, a policy and a destructive `git branch -D`, and it can land once real
  archives exist to expire. The store's schema should not make it awkward later.
- **The v1 migration seed** (§7b: a one-time read-only read of v1's workspaces
  offering its cwds as Scratch sessions). Scratch itself is in scope; seeding it
  from v1 is a separate, self-contained piece, and dogfooding does not need it.
- **MCP.** §7b is explicit: CLI-first, no MCP in v2.0. It is a thin later adapter
  over the same command registry — not a gap M3 fills.
- **Multi-window**, **promote-Scratch-to-task**, and the **repo-project model
  alongside tasks** (§4's "ship both, let usage decide") — all deliberately later.
- **The sheep silhouette** (Flock rule 8). The dot + micro-label is the
  rule-sanctioned fallback and M3 is not blocked on artwork.
